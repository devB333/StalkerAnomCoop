## How a client equips and uses items (source)

| Path | Engine entry | What it sends |
|---|---|---|
| Anomaly's Lua inventory UI: Equip / Unequip (`ui_inventory.script` `Action_Equip`, `Action_UnEquip`) | `db.actor:move_to_slot/belt/ruck` (`script_game_object_inventory_owner.cpp` `MoveItemToSlot`, `MoveItemToRuck`; an occupied slot's item is moved to the ruck first) | `GEG_PLAYER_ITEM2SLOT` (u16 item, u16 slot, u8 do-not-activate) / `ITEM2BELT` / `ITEM2RUCK` to the in-process server, which broadcasts it back; `CActor::OnEvent` (`Actor_Events.cpp:186-270`) applies `CInventory::Slot/Belt/Ruck` |
| Lua UI: Use (`Action_Use`) | `CInventory__eat(obj)` (`_g.script:1174`: `actor_on_item_before_use`), then `db.actor:eat(obj)` → `CInventory::Eat` **directly** (`script_game_object.cpp:1102`; no event) | nothing: `Eat` → `CEatableItem::UseBy` (influences, boosters, a use spent), `eUseObject` → `actor_on_item_use`; a used-up item `SetDropManual` → next inventory update `GE_OWNERSHIP_REJECT` → `OnH_A_Independent` → `DestroyObject` |
| Engine UI (`UIActorMenuInventory.cpp:85-127`), quick-use key (`ActorInput.cpp:247-251`, `CInventory::ClientEat`) | events | `GEG_PLAYER_ITEM_EAT` (u16 item) → server → `CActor::OnEvent`: `_G.CInventory__eat`, then `Eat` |

**Defect found (pre-existing since S08-T02):** on a co-op client the Lua UI's
Use ran `CInventory::Eat` locally (effects on the replica's actor, the
`actor_on_item_use` handlers), and the used-up item's own
`GE_OWNERSHIP_REJECT` was taken by the S08-T02 hook for a **drop intent**: the
server would have put the eaten item on the ground. Fixed: `CInventory::Eat`
refuses on a replica and turns the player's own use into the use intent.

## The actions

| Kind | Validation (server state at that tick) | Apply | Record |
|---|---|---|---|
| 9 equip | own live actor; the item a current online item of **its own inventory** (else 14), not used up or moving (8, 9); place 1–3, slot 1…LAST_SLOT for place 1, flags bit 0 only (else 2); slot: the installed UI's slot table (pistol 1/2/3, rifle 2/3, else its base slot) **and** `CanPutInSlot` (free, outfit allows helmet/backpack); belt: `CanPutInBelt` (belt width from the outfit); ruck: `CanPutInRuck` (else 20) | `CInventory::Slot/Belt/Ruck` on the server's actor | `equip`, **before** the apply |
| 10 use | as above; an eatable item with something left (else 21) | inside the player's script context (`ScriptContextScope(actor, "item-use")`): the player's booster memory selected, `_G.CInventory__eat` (refusal 22), `CInventory::Eat` (its `eUseObject` goes to the installed binder's handlers on the script host actor, inside the context) | `use`, **after** the apply, before the answer: the item's uses left or its release, every other inventory item the use created, released, spent or moved (by diffing the actor's children and uses), the actor's condition |

Phases as for the S08-T01/T02 actions: a known operation returns its stored
outcome; a refusal commits nothing; failpoints
`equip:before-append|after-flush|after-apply|after-ack` and
`use:after-apply|before-append|after-flush|after-ack`. A used-up item is
refused to every other action (8) from its use until the engine has released
it, so a use and a transfer of one item resolve to one outcome.

**Replay** (contract §6): equip — the item in the recorded place (already
there, gone or moved out since: nothing; level objects not there yet:
deferred ≤ 10 s). Use — created items re-created in the actor under their
EntityIds, moved items moved by the transfer adapter, released items released
wherever they are, remaining uses set on the level object, then the actor's
five condition values and the item's boosters (full time). Before the replay
the server collects every item a replayed use releases: a `pickup` or
`transfer` record of such an item is not re-applied (`consumed-later`), which
is what closes **L39** (a used item no longer comes back with its pickup record).

**Presentation.** CampaignEvent 9 carries each participant actor's inventory
layout (every item's place, slot and remaining uses), sent when the server's
layout hash changes (at most every 5 ticks per actor), before every
item-graph point, and to a client entering the world; the client applies it
to its replica (ruck, then belt, then slots; re-applied when an item's
Reparent arrives later) and refreshes the Lua UI. The item-graph point
(CampaignEvent 8) also carries the layout hash; each client must reach it
within 2 s. An accepted use plays `actor_effects.play_item_fx` on the user's
client; on the server that timeline is a no-op (decision T07-5).

**Booster memory per player (decision T07-4).** `itms_manager`'s "a
stronger booster is still active" check keeps a script-local table; the
installed script fixes wrap the function (the original is
`aaaa_script_fixes_mp.itms_manager_actor_on_item_before_use`). Before each
use the server points that upvalue at the user's own table through the Lua C
API (`lua_setupvalue`; the release engine does not open Lua's `debug` library).

## Revisions at the G08 review (2026-10-27, patch 0052)

The user's answers to the S08-T07 decisions: T07-1…T07-4, T07-6, T07-7,
T07-9 approved; **T07-5** and **T07-8** revised. Both are implemented in
`0052-use-fire-block-and-player-needs.patch` (campaign-291 / client-190).

**No firing while a use's animation plays (T07-5).** A use intent now
carries `u8 flags` (bit 0: the client plays the animation, Anomaly's
"animations" option). When it does, the server ignores that player's fire
key from the use until the installed timeline raises the weapon again
(`configs/plugins/actor_effects.ltx`: the `use_weapon(1)` key, else the last;
food 9.68 s, bandage 4.15 s, medkit 12.8 s); a key still held afterwards is
pressed then. Found on the way: **the use animation never played on a co-op
client**: its settings are read by the installed first-update handler, which
does not run on a replica's actor; the client now reads them when its world
goes live (eq-15 showed `animated=0` for every use; eq-16 `1`). Fixture
round 12: participant 1 eats a conserva and its client holds the fire key
from 0.5 s to 11.5 s after.

**Thirst, sleep and psy health per player (T07-8).** The installed
`actor_status_thirst`, `actor_status_sleep` and `arszi_psy` keep their
state in script-local variables for "the actor". The server keeps one copy
per participant slot and swaps it into those variables whenever native code
enters a participant's script context (a hook on every context entry and
exit, through the Lua C API), back to participant 1's outside contexts; the
scripts' own per-frame updates are unregistered and the server runs each
participant's update every tick in its context; participant 2's copy is
saved in the checkpoint (`m_data.coop_needs`); each client gets its player's
values (CampaignEvent 12) for the HUD indicators and the psy bar, and runs
no survival update of its own. The installed pre-hit handlers (armour, psy
damage) now run in the context of the actor that is hit (they had run as
participant 1's for participant 2's hits).
