# S06-T03 — Predict and reconcile the local actor

**Status: Completed (2026-10-21).** Engine `c57fe5b9` + patches 0001–0033;
protocol v1.3 (`proto-build-29`). Design:
[co-op session](../coop-session.md#own-actor-prediction-and-reconciliation-s06-t03).

## What changed

**Protocol** (workspace files):
- `prediction.h` adds `Reconciler`, which keeps per-input-tick records,
  reconciles against the server's position for the last processed tick,
  shifts newer records, and has a tolerance and a snap distance. It also adds
  `Smoother`, a view offset that halves every 60 ms.
- `InputQueue::processed_tick()` returns the last consumed input tick, or,
  when nothing older is queued, a newer tick refused as invalid; ahead and
  stale ticks never move it. Snapshots now report it as `last_input`.
- v1.3 adds the snapshot component `kAim`: an actor's torso yaw and pitch.

**Engine (patch 0033)**, 10 files: `Actor.h`, `ActorCameras.cpp`,
`Actor_Movement.cpp`, `CampaignActorControl.cpp`, `CoopClientLink.cpp`,
`CoopConfig.{h,cpp}`, `CoopReplica.{h,cpp}`, `CoopServerHost.cpp`.
- **Native prediction.** On a replica that predicts (profile `predict = 1`,
  the default), `campaign::controls_actor` lets the client's own actor through.
  `CActor::shedule_Update` then runs the same control path as the server
  (`g_cl_CheckControls`, `g_cl_Orientate`, `g_Physics`) against the same level
  and the snapshot-placed creatures.
  - The input sampler records the actor's position at each input tick.
  - The native path clears the keys; the test driver's keys go in every
    frame.
- **Reconciliation.** After each complete snapshot, the server's position
  for the own actor (from the snapshot's frame, whether or not it changed) is
  compared with the record for `last_input`.
  - Errors under 3 cm are left alone.
  - Larger errors move the physics controller at once (the collision state).
    A camera effector (`CoopViewEffector`) keeps minus the correction and
    halves it every 60 ms.
  - Errors over 1.5 m jump with no smoothing.
- **Resets.** A Welcome (new connection) or a world start clears the records
  and the view offset. Input ticks restart with the connection.
- **Found and fixed in this task:**
  1. *Refused inputs were never reconciled* (pred-1). In leg G the server
     refused every input (Prone) and kept `last_input` on the tick before the
     leg. The client walked 1.5 s uncorrected and then snapped 3.95 m. Fixed by
     `processed_tick`: G now peaks at 0.12–0.18 m and converges.
  2. *The other player's arms stayed centred while that player looked around*
     (user report). The remote actor's torso was set to its body yaw. Actors
     now carry `kAim`, set by `CActor::replica_set_aim`.
  3. *The own first-person arms snapped to the centre and drifted back when
     turning* (user report; it persisted after fix 2). `CActor::cam_Update`
     keeps the previous camera angles for the HUD turn rate
     (`fFPCamYawMagnitude`) in function statics. A co-op client updates both
     actors there every frame, so the view actor's turn rate was the gap
     between the two cameras, and the HUD weapon's turn tilt
     (`CHudItem::m_fLR_CameraFactor`) went to its limit. Now only the view
     actor updates them (`ActorCameras.cpp`); single-player has one actor.
     - Measured with the camera still: the turn rate was up to 1,214 and
       6,614,999 rad/s on the unfixed diagnostic build (hud-1,
       campaign-181/client-86).
     - After the fix it was **0.000 on both clients** over 3,287 and 3,448
       still frames (hud-2, campaign-182/client-87).
     - The user confirmed the snapping is gone.
- **Test driver.** Leg P walks locally while telling the server to stand (a
  deliberately wrong prediction). `script-leg-first-move` records how long
  after a leg begins the own actor has moved 5 cm.
- **Tools.** `tools/compare-coop-prediction.py` (new);
  `prepare-coop-session.py --no-predict`.

What this shows, against the acceptance criteria:
- **Deliberately wrong local predictions converge to server state.** In G
  and P the client walked while the server did not. The error stayed at
  latency size (at most 0.28 m) and fell to within 4 cm once the leg ended.
- **Old input cannot affect a new epoch.** Unit test `reset-forgets-old-input`.
  In session-8, client 2's rejoin restarted its input ticks at 1, its first
  reconciled snapshots had error 0.000, and there were no unknown or snapped
  corrections.
- **Latency/loss and correction metrics** are above. The 83–100 ms is mostly
  the native controller accelerating from rest; without prediction the same
  measure is 250 ms (render delay, snapshot interval and the round trip).

**Rule change after seeing data:** the responsiveness bound was a median of
at most 60 ms before pred-3. pred-3 measured 83–100 ms with prediction and
234–250 ms without, and the controller alone needs about 60 ms to cover 5 cm
from rest. The bound became 120 ms before the final runs (pred-8/9).

## Limits

- Prediction is movement only: no jump, lean or climb (not in the input
  model, L01). Weapons and inventory are not predicted; their state comes from
  the server (S06-T04, S08).
- The client predicts with its own copy of stamina (not replicated) and its
  own collision against creatures placed from snapshots 100 ms in the past. A
  push by an NPC on the server arrives as a correction (Fanat in pred-10).
- The view offset is visual only; the third-person body seen by the other
  player follows the server's snapshots, not this client's prediction.
- The HUD fix restricts one function's statics to the view actor. Other
  engine code may still hold single-actor statics; none were found in
  `cam_Update`, `player_hud` or `CHudItem`.
- One host, loopback, simulated impairment only (L16).
