# S07-T05 — Resynchronize clients after restored authority

**Status: Completed (2026-10-23).** Engine `c57fe5b9` + patches 0001–0042;
protocol `proto-build-35`. Spec: [persistence contract](../persistence-contract.md)
§2 (epoch), §8. Run shared with [S07-T04](S07-T04.md) (rec-3).

## Deliverable (patch 0042)

- **Epoch per incarnation** (server): the recovery allocates `highest seen
  + 1` and writes it to the journal before the server listens
  (S07-T04); `ServerConfig.authority_epoch` and every `ResyncBegin` carry
  it. A resume request for a pre-restart session is refused by the session
  layer (the server's session table is empty: fresh session, `resumed=0`).
  The epoch is in every message header, so a stray old-epoch packet is
  dropped by the guard; a new connection also has new transport keys.
- **Client fence and reconnect** (`CoopClientLink.cpp`): on `Ended` (not
  quitting, not the S05-T01 injection test) the client **leaves its
  world** with the engine's `disconnect` (the level is destroyed: no input
  is sampled, the replica ends, nothing of the old world is kept), keeps
  its unacknowledged operations pending, and reconnects with backoff 1 s
  doubling to 10 s (`reconnect-scheduled`, `reconnect attempt=N`) until its
  exit time; a reconnect waits until the stale world is gone
  (`world-ended … level=0`). On `Welcomed` the backoff resets, the resync
  tracker is new, and an epoch change is logged (`epoch-changed from=1
  to=2`). The server streams a full world from a fresh generation, as for
  any join, with `event_watermark` = that generation's revision, so the
  client's applied revision restarts at the checkpoint's.
- **Stored outcomes**: a retried operation the previous incarnation had
  committed is answered from the operation index with its original
  revision (`ledger-duplicate`, S07-T03); one never committed is evaluated
  afresh.

Server side: `recovery … generation=5 … replay=50 … index=183`,
`recovery-replayed records=50`, both actors reassigned, `ledger-state`
1509 / 495, equal to the last committed `money_after` of each slot

connection's keys are gone with the transport session, and the header
epoch 1 would be dropped by the guard (S04-T03 `guard.h`); S04-T05's
`stale-connection-cannot-submit` tests cover the same-process variant.

## Limits

- The stale-outcome path (a retry answered from the index with its original
  revision) is exercised by S07-T06's `commit:after-flush` and
  `commit:after-apply` runs, not here: in rec-3 every operation the server
  had committed was also acknowledged before the kill.
- The client notices the loss through the liveness timeout (15 s) and the
  server's restart takes ~30 s (load 19 s), so a player is out of the world
  for about a minute; no "reconnecting" UI yet (the main menu shows while
  the level is gone).
- A client that fails to reconnect keeps trying every 10 s until its exit
  time; nothing of the old world survives on it (contract §8).
