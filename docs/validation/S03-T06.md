## Question

AI vision scales a target's visibility by the target's luminosity
(`CVisualMemoryManager::object_luminocity`, `xrGame/visual_memory_manager.cpp:322-328`),
read from the object's render-specific data (`CROS_impl`). The headless server
never rendered, so every luminosity stayed at its constructor's 0
(`Layers/xrRender/LightTrack.cpp:23`) and AI saw every target as in darkness
(S03-T04). Can the server compute what the client computes, CPU-only, for each
participant? **Acceptance** (plan.md S03-T06): participant actors' luminosity
follows sun, sky, weather and static lights, matches the client's for the same
checkpoint within a stated tolerance, and AI vision uses it.

## What the client does (source)

- `CROS_impl::update` (`LightTrack.cpp:180-293`): a sample point at the
  visual's bounding-sphere centre raised by 0.3 of its radius; one ray toward
  the adapted sun (`calc_sun_value`, `:376`, `rqtBoth`, 500 m); 26 fixed sky
  directions sampled 5 per update (`calc_sky_hemi_value`, `:398`, `rqtStatic`,
  50 m); the level's static hemi lights in range, each with an occlusion ray and
  attenuation (`prepare_lights`, `:449`; only `flags.bStatic` lights count on
  DX11, `:466-475`, so flashlights, campfires and lamps never did); summed with
  the environment's ambient, sky and sun colours; the sun and sky terms are
  smoothed with a 1 s time constant (`update_smooth`, `ps_r2_lt_smooth = 1`).
  Luminosity is the brightest channel, clamped to 1 (`LightTrack.h:83-88`).
- Which objects: each rendered frame, the view entity and one renderable of the
  camera frustum, front to back, in turn (`xrRenderPC_R4/r4_R_render.cpp:30-63`).
- Inputs the server lacked: the lights (`CLight_DB::Load/LoadHemi`, loaded by
  the render level the server skips, `IGame_Level.cpp:134-139`); the sun aimed
  from the environment (`CLight_DB::Update`, run in the client's render
  calculate); the weather/time-of-day blend (`CEnvironment::OnFrame` → `lerp`,
  `calculate_config_sun_dir`) — the server never runs the persistent frame
  (S02-T05a), so the environment never advanced; the level's environment
  modifiers apply at the camera position (`CEnvironment::lerp`, `level.env_mod`
  exists on k00_marsh). The light objects themselves are CPU objects in the
  spatial database (`light.cpp`), the blend's render mixer only copies texture
  handles (`dxEnvironmentRender.cpp:143-160`), and the game time is already set
  every level frame (`Level.cpp:1179`).

## Change

- `xrEngine/Render.h`: `cpu_lighting_load/unload/sun/track` (no-ops by
  default, like the existing `cpu_models_*`); R4 implements them
  (`xrRenderPC_R4/r4_loader.cpp`): `Lights.Load` and `LoadHemi` from the level
  stream, `Lights.Unload`, `Lights.Update`, `CROS_impl::update` on an object.
  `CLight_DB::hemi_count`.
- `xrEngine/IGame_Level.cpp`: the campaign server loads the CPU lighting where
  the client loads the render level, and unloads it before the level (and its
  spatial space) goes.
- `xrEngine/Environment.{h,cpp}`: `CEnvironment::UpdateCPU` — `lerp` (with the
  modifiers at `Device.vCameraPosition`) and `calculate_config_sun_dir`; no lens
  flare, rain, thunderbolt or render state.

  the server (`Level.cpp`): for each participant actor, the camera position

  actor is tracked, and one object of its view frustum (built from its active

  the camera position is restored. Counters and timing.

## Acceptance

- **Follows sun, sky, weather and static lights:** the environment blends at
  each actor's eye from the current weather and game time; sun and sky rays
  against the level geometry; the level's static point lights (none on
  k00_marsh). Different exposures give different values (0.0335 vs 0.1448).
- **Matches the client within a stated tolerance:** at steady state the server
  and the normal client read the same actor at the same checkpoint as 0.0213
  and 0.0213 (tolerance 0.03 absolute or 10 %, sky term 0.05).
- **AI vision uses it:** `object_luminocity` of real observers reads the
  participants 14–42× brighter than before; awareness and combat stages pass.
- No constant was substituted; no NPC other than each participant's view
  pick is refreshed (user decision).

## Limits

- Only participant actors and one object per participant view per tick are
  tracked, as on a client for its own player. An NPC outside every
  participant's view keeps its last value (0 if never seen), so NPC-vs-NPC
  sight of unviewed NPCs stays as dark as it is off-screen on a client.
- The view frustum assumes a 16:9 window and the camera's own FOV; a
  server-driven participant's camera keeps its last yaw until Stage 4 delivers
  views, so its "facing" pick follows that yaw.
- The environment blend runs once per participant per tick; `CurrentEnv` ends
  each tick as the last participant's (modifiers at that eye).
- Dynamic lights (flashlights, campfires, lamps) count neither on the DX11
  client nor here.
- Behavioural side effects of lit vision, all observed: the Clear Sky guards
  now engage a monster beside actor 1 (S03-T04 fixture adapted); the installed
  campfire hint reached the server's UI (fixed as a presentation); smoke-143's
  commanded stalker stopped mid-walk once in nine light-model runs (never in
  the 37 recorded runs before it). Its cause is not established; the planner
  stayed on script control while the weapon handler changed. Recorded as a
  watch item for S02-T04c's fixture.
- capture-21's client start-up hang is unexplained and unrelated to the level.
- G02 regression rule: smoke-144 passes all 66 stages from the final source.
