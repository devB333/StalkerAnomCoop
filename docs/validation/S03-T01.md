# S03-T01 — Stable participants and authoritative contexts

Recorded 2026-10-18 UTC. **Status: Completed (2026-10-18).** The identity model,
the engine-id mapping and the participant registry are defined in
[participant-identity.md](../participant-identity.md) and implemented in
patch 0021. Four unit fixtures run inside the campaign server binary
(`Run-Stage2Smoke.ps1 -Scope Identity`) and a level identity check runs in the
GameState smoke after the first ticks. Source `builds/build_1/engine-work` at
`c57fe5b9` with patches 0001–0021; citations relative to `src/`.

## Question

Plan.md S03-T01: separate persistent identity from engine slots and views.
Define campaign/player/party/entity/item ids and a generation-aware mapping
over the engine's recycled u16 ids; implement a runtime participant registry
with two active slots as policy, explicit action context and server/client
role boundaries. **Acceptance:** two identities cannot alias through recycled
u16 ids; no client-supplied identity becomes authority by assertion.
**Validation:** unit fixtures for slot reuse, disconnect identity retention
and role/context misuse.

## What the engine does (source)

- **u16 entity ids are recycled.** `xrServer::m_tID_Generator` is
  `CID_Generator<u32,u8,u16,u8,u16,0,u16(-2),256,u16(-1)>` (`xrGame/xrServer.h:145-158`).
  `vfFreeID` pushes a freed id onto its 256-id block and stamps the block with
  the free time (`id_generator.h:106-125`); `tfGetID()` takes the block with
  the oldest stamp and pops the last-freed id (`id_generator.h:97-104`,
  `operator<` at 35-38). Script releases free with time 0
  (`alife_simulator_script.cpp:199,318,451`); destroyed entities free with
  `Device.TimerAsync()` (`xrServer.cpp:873`). Online entities and all ALife
  objects draw from this one generator (`alife_simulator_base.cpp:107,165,209`,
  `alife_storage_manager.cpp:152`, `alife_switch_manager.cpp:95`,
  `xrServer_process_spawn.cpp:79-112`): smoke logs show ~1,100–1,200 server
  entities against ~26,260 ALife objects.
- **The ALife switches free and re-request an object's own id.** Going
  offline: `Perform_destroy` → `entity_Destroy` (`FreeID`) then
  `object->ID = PerformIDgen(object_id)` (`alife_switch_manager.cpp:91-95`).
  Going online: `entity_Destroy` then `Process_spawn` re-requests `E->ID`
  (`alife_switch_manager.cpp:52-62`, `xrServer_process_spawn.cpp:112`).
- **A connection is a `u32 ClientID`** (`xrCore/client_id.h`); the in-process
  client is `ClientID 1` / `single_player` (`xrServer.cpp:1040-1048`), created
  by the client loading stages (`Level_network_start_client.cpp:55-57`), and
  the privileged imports are gated on `bLocal` (`xrServer_process_update.cpp:14,66`).
- **The player is one global**, `g_actor`, set by spawn flags
  (`Actor_Network.cpp:530-531`); `Actor()` asserts single player (58-67).

## Acceptance

- **Two identities cannot alias through recycled u16 ids.** Observed with the
  engine's generator: immediate reuse of a freed id (and 1,000 of 1,000 after a
  bulk release) never resolved an old key to the new object; in the loaded
  campaign every online and ALife object's binding matches the entity id
  stored on the object and no binding is orphaned.
- **No client-supplied identity becomes authority by assertion.** Mutations
  need a token only a server-role registry mints; a client intent is
  authorized against its session's participant, refused when it names another
  participant, arrives on the bridge or an unknown session, or asks for an
  identity or world scope.

## Limits

- Fixture identities only: `PlayerId`/`PartyId` come from the harness. The
  authenticated binding of a connection to a player is S04-T04; liveness and
  when a detached participant is released is S04-T05.
- `EntityId`s live for one process: a checkpoint reload re-creates the objects
  with new ids (the stored id is not in the save). Stage 7 owns the mapping.
  The participant bound to the actor in the GameState smoke therefore holds a
  stale actor key after the checkpoint restarts; nothing reads it yet.
- The client build has no registry (`g_campaign_identity` null); S03-T02
  decides the client's role and replaces `Actor()`/`CurrentEntity()` in
  gameplay code. The privileged `bLocal` import bridge is unchanged.
- One registry per process; two slots as policy. Nothing persists.
- No `tests/` directory yet: WSL has no C++ compiler, so the unit fixtures run
  inside the campaign server binary as a smoke scope.

## G02 regression rule

The GameState smoke ran with the hooks active from the final-form build (smoke-99: all 60 stages) and the final source (smoke-101 and smoke-102: `campaign-hearing-failed`, identity check passed in both; smoke-103: all 60 stages). G02 is not reopened: the two failures have the cause below, which predates this task (smoke-94 shows the same 12/0/12/15 counts) and is outside anything patch 0021 touches.

**Hearing-stage variation, cause found (smoke-99/101/102/103 captures).** The hearing fixture passes on `npc_walk_events > 0`: AI sound events from the walked stalker during the walk phase. In every server run those walk-phase events are `weapons\rifle_holster` / `weapons\ak\ak_draw` (the stalker holstering and drawing its rifle while walking), never `material\human\step\*`; in the failing runs the stalker simply did not handle its weapon during the walk (0 phase-1 rows), in the passing runs it did (5 rows). The stalker's 12 footstep events are all in the observe phase. The normal client's capture (`builds/logs/S02-T05c/run-capture-08/client-hearing.csv`) has 32 phase-1 rows for the same stalker, footsteps included. So the criterion is satisfied by an incidental AI decision, and the server registers no footstep sound events for the scripted walk while the client does. Not an identity effect (the hooks touch no sound, step or AI path; the identity check passed in all four runs). Open item for S03-T04 (participant-aware AI and hearing): find why the server's scripted walk emits no footstep events, and change the fixture's criterion to footsteps once it does.
