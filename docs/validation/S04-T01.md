# S04-T01 — Validate GameNetworkingSockets in isolation

Recorded 2026-10-20 UTC. **Status: Completed (2026-10-20).** No engine change
(no patch). The probe and its build and run scripts are project tools outside
`engine-work`: `tools/network-probe/` (`pins.json`, `probe.cpp`,
`CMakeLists.txt`), `tools/Build-NetworkProbe.ps1`, `tools/run-network-probe.py`.
GameNetworkingSockets (GNS) source citations are relative to the pinned
checkout `builds/network-probe/src/GameNetworkingSockets` at `d534c19a`.

## Question

D6 picked GNS provisionally, "subject to an isolated toolchain test"
(plan.md D6, R05). **Acceptance** (plan.md S04-T01): GNS works with the
accepted compiler and runtime; reliable traffic survives loss; stale
transient data can be discarded without blocking critical traffic. Also
asked: connect, disconnect, reconnect traces, threading and packaging needs,
and NAT/deployment expectations.

## Decision

**GNS v1.6.1 is accepted for S04-T02**, built as recorded below. It builds with
the Stage 1 pinned compiler (no warnings), its DLL adds no dependency the
engine does not already load except Windows' own `bcrypt.dll`, and every probe
scenario and both GNS self-tests pass (final run **net-8**). Five findings are
inputs to the S04-T02 adapter and S04-T05 liveness work (see
[Findings for S04-T02/T05](#findings-for-s04-t02t05)).

## Threading (source and observed)

- `GameNetworkingSockets_Init` starts one service thread
  (`steamnetworkingsockets_socketthread.cpp:3828-3829`). Observed in every
  process: 4 threads before init, 5 after. It does the socket I/O, encryption
  and paced sending (`k_nSteamNetworkingSend_UseCurrentThread` doc,
  `steamnetworkingtypes.h:1031-1044`).
- Connection status callbacks are queued by the service thread and run only
  inside `RunCallbacks()` on the calling thread
  (`csteamnetworkingsockets.cpp:1715-1757`). Observed:
  `callbacks_off_main_thread: false` in every process. More than 100 pending
  callbacks trips an assert (`:1773`), so the owner must poll regularly.
- Received messages are pulled with `ReceiveMessagesOnPollGroup` /
  `ReceiveMessagesOnConnection` on the caller's thread and belong to the
  caller until `Release()`.
- The debug-output callback can run on the service thread (the probe guards
  its output with a mutex).
- Alternative: manual poll mode (`SteamNetworkingSockets_SetManualPollMode`,
  `SteamNetworkingSockets_Poll`, `socketthread.cpp:4291-4320`) runs the
  library on a thread we own instead of its service thread. Not tested.

## Packaging

- Ship `GameNetworkingSockets.dll` (1.6 MB) next to the executable, or link
  `GameNetworkingSockets_s.lib` plus `libprotobuf.lib` statically. The DLL
  keeps GNS's compile flags (`/EHs-c-`, `/GR-`, `GOOGLE_PROTOBUF_NO_RTTI`,
  `CMakeLists.txt:182-226`) and protobuf out of the engine's projects.
  Recommendation for S04-T02: the DLL, used only from the adapter.
- Include the GNS and protobuf BSD-3-Clause notices (both `LICENSE` files)
  with any distributed binary.
- No new runtime: the VC++ 2015–2022 runtime the engine already needs.

## Deployment expectations

- Dedicated server listens on one UDP port; clients connect by `address:port`
  (`CreateListenSocketIP`, `ConnectByIPAddress`). No relay, no P2P/ICE, no
  Steam. A server behind NAT needs that UDP port forwarded and a Windows
  Firewall inbound rule; clients need only outbound UDP. IPv4 tested; IPv6
  (supported since v1.6.0) untested.
- Every connection is encrypted (AES-GCM with an ephemeral key exchange) but
  **unauthenticated**: the open-source build allows unauthenticated peers by
  default (`IP_AllowWithoutAuth = 2`, `csteamnetworkingsockets.cpp:88-92`) and
  we have no certificates. That is protection against eavesdropping, not
  against an active man in the middle, and it identifies no player. Player
  identity is S04-T04's job (plan.md R06): either GNS certificates from our own
  CA, or application credentials over the encrypted channel with that limit
  stated.

## Findings for S04-T02/T05

1. **Dead-peer detection depends on traffic.** GNS starts its timeout clock
   only when a packet that expects a reply goes unanswered, and only then
   counts `TimeoutConnected` (`steamnetworkingsockets_connections.cpp:3590-3605`).
   A silent server sends its first keepalive 10 s after the last receive
   (`steamnetworking_statsutils.h:57`), so a dead idle peer took 15.5 s with a
   5 s timeout (crash-idle). Unreliable traffic asks for no ack, so a 20 Hz
   unreliable heartbeat still took 12.5 s (net-3; the timeout started at the
   next 5–7 s stats ping, `statsutils.h:41-42`). A reliable heartbeat gives
   timeout + about 0.5 s (net-4, net-8). S04-T05 needs a reliable heartbeat
   or its own application timer, never unreliable traffic alone.
2. **A dead session holds its slot until it times out.** The transport gives
   a reconnect a new connection and cannot tell it is the same player. With
   a two-slot cap the replacement is refused until the dead session times out
   (net-2 and net-3, silent or unreliable traffic: refused for 7.5 s, until
   the other player happened to leave;
   net-8: admitted 5 s later, after the timeout). S04-T04/T05 must bind a
   reconnect to the player's identity and replace the stale session instead
   of counting it.
3. **The send buffer is shared per connection.** When snapshots fill it
   (512 KB default, `csteamnetworkingsockets.cpp:78`), *reliable* critical
   sends are refused too (`k_EResultLimitExceeded`, phases 2–3). And
   `k_nSteamNetworkingSend_UnreliableNoDelay` does not drop data that's merely
   queued (`steamnetworkingtypes.h:997-1013`). So the adapter must bound
   unreliable data itself (as the probe's queue-time rule does) and treat a
   refused critical send as an error. Better still, budget snapshots below
   the measured send rate. Under 1% loss on a saturated link the critical
   tails grew (p95 103–148 ms against 37–74 ms baseline) even with the rule,
   while medians held.
4. **Reliable order is per lane.** One lost reliable message delays the later
   ones on its lane until it is resent (the 1% loss tails above).
   Independent reliable streams that shouldn't wait for each other belong on
   separate lanes. Lane order is not a gameplay order (plan.md S04-T02 risk).
5. **Windows power throttling defeats a sleeping poll loop.** A windowless
   background process can be power-throttled on Windows 11, which then
   ignores `timeBeginPeriod(1)`. `Sleep(1)` became 15.5 ms and every reply
   waited about 15 ms in the receive queue (net-4: loop gap p50 15.5 ms; net-5
   onward, after opting out with `SetProcessInformation(ProcessPowerThrottling)`:
   2.0 ms). The headless campaign server is this kind of process. Its network
   polling (and its frame clock) must opt out or not depend on `Sleep`
   granularity. Not checked on the campaign server itself.

## Limits

- **One machine, loopback only.** No separate-machine, LAN, internet, NAT or
  firewall test was available. Loss, reordering, duplication and lag are
  GNS's simulation, not a real network. No claim of internet reachability.
- Short runs (≤ 35 s per scenario). GNS's `soak` test and long sessions were
  not run.
- Two peers per listener (three in `basic`). No load beyond 128–256 KB/s per
  connection.
- protobuf 3.21.12 dates from 2022-12 and isn't the current protobuf release
  line. It parses handshake data from unauthenticated peers inside GNS.
  Moving to a current protobuf means adding Abseil to the build. Revisit
  before release (S04-T04 or G11).
- BCrypt is GNS's least-used crypto backend (upstream supports it mainly for
  Xbox). v1.6.1 fixed leaks in it, `test_crypto` passes, and every session was
  encrypted. If it causes trouble, OpenSSL is the documented alternative (one
  more DLL to ship).
- Manual poll mode, IPv6, GNS certificates and the static library were not
  exercised.
- Builds are not byte-reproducible across build directories.
