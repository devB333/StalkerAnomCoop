# S02-T03d — Skeleton collision, hit picking and physics shell on the loaded level

Recorded 2026-10-18 UTC. **Completed.** On the loaded level (S02-T05d), with no
graphics device, every alive entity (the actor, 21 stalkers, 14 monsters) has a
skeleton collision form built from its animated bones and a physics character
controller; 491 skeleton forms with 1,780 elements and 247 physics shells with
264 elements exist; the actor's ray picks hit its head, its chest and the ground
through the object space as a bullet trace would. The normal client, loading the
same save, produces **the same structure for every common object**: sections,
visuals, bone counts, visible masks, element counts, shape types, local shape
sizes, character flags, foot radii, boxes and masses, shell element and
geometry counts and masses are identical (one lamp differs by its on/off
state). The actor's trunk hit boxes agree within 2.3 cm and its top pick hits
the same head bone within 3.9 cm. With this, S02-T03's four suffix tasks are
done and the parent task completes.

Not shown here: a bullet actually hitting and damaging an entity, ragdoll
creation on death, and the falling-body physics step (S02-T04b, S02-T06).

## What the native spawn already creates (source)

- **Skeleton collision form.** `CObject::net_Spawn` creates `CCF_Skeleton` for
  any object whose section has `cform` and a visual (`xrEngine/xr_object.cpp:263-270`);
  it asserts on a missing visual. The constructor asserts the visual has
  kinematics (`xrEngine/xr_collide_form.cpp:115-126`). `BuildState` runs once per
  frame on the first ray query: it calculates bones, then builds one element per
  visible bone with a pickable shape (box, sphere or cylinder), transformed by
  the bone's current transform and the object's `XFORM()`
  (`xr_collide_form.cpp:128-211`). Hit transforms are therefore animation-driven.
- **Hit picking.** `CObjectSpace::_RayPick` tests the static CFORM, then every
  collidable object the spatial database returns along the ray, through its
  collision form's `_RayQuery` (`xrcdb/xr_area_raypick.cpp:145-200`).
  `CCF_Skeleton::_RayQuery` rejects by bounding sphere, then tests every element
  (`xr_collide_form.cpp:228-283`). The bullet manager uses the same path and
  reads the hit bone back from the result (`xrGame/Level_bullet_manager_firetrace.cpp:38-140, 374-400`).
- **Character controller.** `CCharacterPhysicsSupport::in_NetSpawn` plays the
  spawn cycle, calculates bones, then enables and positions the movement
  control's character (`xrGame/CharacterPhysicsSupport.cpp:184-249`). The ODE
  capsule is created by `CPHMovementControl::CreateCharacter` from the actor's
  spawn (`Actor.cpp:297`) or lazily for NPCs (`CharacterPhysicsSupport.cpp:251-261, 326`).
- **Physics shells.** Live characters have no shell; `CreateSkeleton` builds the
  ragdoll from the kinematics on death (`CharacterPhysicsSupport.cpp:700-731`).
  Items and physic objects with no parent build their shell at spawn
  (`xrGame/physic_item.cpp`, `CPhysicItem::net_Spawn` → `setup_physic_shell`;
  `xrGame/PhysicObject.cpp:478-505`, `CreateBody`).

None of these touch the renderer, which is why no engine change was needed for
them in the campaign server; the S02-T03a–c and S02-T05 patches already supply
the models, bones and physics world they read.

## Ownership and lifetime

| Object | Owner | Created | Destroyed |
|---|---|---|---|
| `collidable.model` (`CCF_Skeleton`) | `CObject` | `CObject::net_Spawn` | `CObject::net_Destroy` (`xr_object.cpp:280-283`) |
| `CCharacterPhysicsSupport` | the entity (`Actor.cpp:2847`, `ai_stalker.cpp:1415`, `base_monster.cpp:66`) | with the entity | with the entity |
| `CPHMovementControl` and its `CPHCharacter` | the support object | support constructor; character on `CreateCharacter` | `in_NetDestroy` / support destructor |
| ragdoll `CPhysicsShell` of a character | the support object (`m_pPhysicsShell`) | `ActivateShell` on death | `in_NetDestroy` / destructor (`CharacterPhysicsSupport.cpp:138-142, 355-358`) |

This task changes none of those owners; the capture only reads them.

## Method

Patch `0011-collision-capture.patch`
(SHA-256 `c6b88dca14a4fdaad60914b5e7f362b5864198df42b33e15a34ec05d4cb6d518`).
The series reconstructs all 61 changed files byte for byte in
`builds/stage2/patch-check-12b` (`builds/logs/patch-reconstruction-12.json`).
The patch adds `xrGame/CampaignCollisionCapture.{h,cpp}` and wires them into
`xrGame.vcxproj`, `xrEngine/x_ray.cpp` (the smoke stage) and
`xrGame/GamePersistent.cpp` (the client's opt-in frame hook); no engine behaviour
changes.

**Shared capture, `xrGame/CampaignCollisionCapture.{h,cpp}`.** Every object on
the level is visited in ID order:
- for each `CCF_Skeleton`: the vertical line through the form's bounding-sphere
  centre is queried from above against the form itself (this builds the frame's
  state and gives the `self` row), then every element is written with its bone,
  shape type, local shape parameters and its centre in the owner's space; the
  character controller's existence, foot radius, box and mass are written; the
  same ray is picked through the whole object space (`top`, `rqtBoth`);
- for the actor, two more picks: chest height from two metres in front
  (`front`), and the static ground under the feet (`ground`, `rqtStatic`);
- for each physics shell: element and geometry counts, mass, active and enabled
  state, and per-element bone, geometry count and mass.

The capture fails explicitly when an alive entity has no skeleton form, no
element or no character, when the actor's three picks do not hit, when a shell
has no element, or when any value is not finite. A shell without mass is counted
(see Results, smoke-53).

**Server.** `xrCampaignLevel_CaptureCollision` runs after `campaign-ticked`;
stage `campaign-collision-passed` (exit 13 on failure). `Run-Stage2Smoke.ps1`
expects the stage for GameState and copies the CSV to the run log as
`server-collision.csv`.

**Client.** `tools/Run-ClientCollisionCapture.ps1 -Run <run>` (runtime from
`python3 tools/prepare-stage2-smoke.py <run> S02-T03d`) starts the rebuilt
client with `-s02-collision-capture -start server(player - autosave/single/alife/load) client(localhost)`
(`-start` runs the rest of the command line as a console command,
`xrEngine/x_ray.cpp:629`). One second of device time after the actor spawned
and precache finished, `CGamePersistent::OnFrame` runs the same capture and
quits. Without the flag the client is unchanged. The accepted runtime is only
read; its DLLs, settings and shader cache are copied into the isolated runtime.

**Compare.** `tools/compare-collision-capture.py <server.csv> <client.csv> [pose_tol]`:
- objects are matched by ID; IDs on one side only are reported with their
  sections, not failed (scripts spawn a varying set of objects while the level
  loads: smoke-52 had 1,090 objects, smoke-53 1,095, smoke-54 1,094, the client
  1,097); exactly one actor must be common;
- structure must be identical for every common object (see the summary above);
  floats within 1e-3, local shape parameters within 1e-5;
- hanging lamps hide their light bone when off and flicker at random
  (`xrGame/HangingLamp.cpp:300-330, 371-450`), so their visible mask and
  element count are reported as lamp state;
- pose-dependent values are asserted for the actor only: trunk elements (pelvis,
  spine, neck, head) within 0.05 m, `top` and `ground` picks with the same hit
  and range within 0.05 m, position within 0.1 m. The actor's limbs and `front`
  pick are reported, not asserted: on the client the actor is the view entity,
  so its arms follow the HUD weapon and its torso the camera (G03). NPC pose
  rows are reported only; their AI runs in real time on the client.

The trunk/limb split, the 0.1 m position tolerance and the lamp rule were
chosen after the first comparison (below) showed those patterns; the structural
rules were fixed beforehand.

## Findings

- **Hand and toe hit boxes far from the body, on both sides.** At capture time
  some stalkers' `bip01_*_hand`, finger and `bip01_*_toe0` elements lie 3–56 m
  from the object's origin (server: 12 objects in smoke-54; client: 13 objects,
  different ones, plus dropped weapons). Both captures show it, so it is native
  behaviour of callback-driven bones (IK legs, `xrGame/IKLimbsController.cpp`;
  stalker bone callbacks, `ai_stalker.cpp:824`) at the sampled frame, not a
  CPU-only regression. Recorded for S02-T04c (activity policy) and G03; not changed.
- **Zero-mass shell.** `awr_tiski` builds a skeleton shell whose root element has
  no geometry and no mass, identically on both sides.

## Limits

- **Picks, not bullets.** The hit path is exercised through `CObjectSpace::RayPick`
  and `CCF_Skeleton::_RayQuery`, which is what the bullet manager calls, but no
  bullet was fired and no damage, impulse or ragdoll was produced (S02-T06, H07).
- **No ragdoll.** Live characters have no shell by design; shell creation was
  observed for the 247 item and physic-object shells, not for a dead character.
- **One frame, one save.** Captured once after 50 server ticks and once one
  second after the client's spawn, on `k00_marsh`.
- **Same code on both sides.** As in S02-T03c, the client capture runs the same
  CPU code on the same data; this shows the renderer-free process builds the
  same collision data, not that the collision system is independently correct.
- **Sound.** The server still logs 1,002 `Couldnt find sounds … characters_voice\…`
  errors while NPCs spawn; the client run of the same save logs none. This
  confirms the cause is in the server's `-nosound` stand-in or lookup, not the
  content (S02-T05c).
- **Client window.** The client capture opens an 800×600 game window and loads
  the level for about a minute.
