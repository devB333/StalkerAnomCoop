# S02-T06 — Native campaign simulation and checkpoint round-trip

Recorded 2026-10-18 UTC. **Blocked** (architecture decision requested; see
the blocker below). This report covers the first S02-T06 item, the actor's Lua
binder on the server, which S02-T04c found not running its first update. The
cause is isolated and the diagnostics are permanent; the fix exposes a
presentation dependency inside the installed scripts' actor callbacks that
needs a decision before the rest of S02-T06 (combat, ALife actor position,
save/reload) is attempted.

## Question

`compare-06-smoke-57` (S02-T04c) showed `objects_per_update` 65534 on the
server against 20 on the client. `bind_stalker.script` `actor_binder:reinit()`
sets 65534 at spawn and the first-update block of `actor_binder:update()`
(lines 207–240) queues the reset to 20, prints `collectgarbage before=` and
sets `db.actor.afterFirstUpdate`. The server log had none of that.

## Diagnostics added (patch 0015)

Patch `0015-actor-binder-diagnostics.patch` (SHA-256
`6e0491d4527fbf0bd61b0cfb4b7d9e1fb4c428f80017326d69734fe0c1096c61`, 5 files:
`xrGame/Actor.{h,cpp}`, `CampaignServerStart.cpp`, `script_binder.cpp`,
`ui/UIActorMenu_script.cpp`). The series reconstructs every changed file byte
for byte in `builds/stage2/patch-check-16b`
(`builds/logs/patch-reconstruction-16.json`).

- **`xrGame/CampaignServerStart.cpp`**, `xrCampaignLevel_ReportTicks`, logs
  after the first 50 ticks: `S02-T06 actor schedule_needed t_min t_max
  schedule_updates processing binder db_actor after_first_update
  binder_check_start` — the actor's scheduler eligibility
  (`shedule_Needed()`), its scheduled-update count (`CActor::s_schedule_updates`,
  new static counter at the top of `CActor::shedule_Update`), whether the C++
  script binder still holds its Lua object (`CScriptBinder::object()`), and
  the Lua side read through luabind: `db.actor`, `db.actor.afterFirstUpdate`,
  `db.actor_binder.bCheckStart`.
- **`xrGame/script_binder.cpp`**: the binder's `try { … } catch (...) {
  clear(); }` blocks deleted the Lua binder silently. xrGame builds with C++
  exceptions off (`ExceptionHandling=false`) and luabind with
  `LUABIND_NO_EXCEPTIONS`, so Lua errors go to `CScriptEngine::lua_error` /
  `lua_pcall_failed` (which is fatal, `script_engine.cpp:266-288`) and never
  reach those catches; what they do catch are structured exceptions (access
  violations) in native code called from Lua. `shedule_Update` now uses an SEH
  filter that logs the exception code, the faulting address and the call
  stack with symbols (dbghelp `SymFromAddr`/`SymGetLineFromAddr64`,
  `CaptureStackBackTrace`) before clearing the binder; the other catches log
  the object and phase.

because the installed scripts' `actor_on_first_update` subscribers include
HUD code that indexes the game UI. Until smoke-66 the native fault was

## Blocker B20 — presentation calls inside the actor's gameplay scripts

Evidence from the installed scripts (`db/configs/scripts.db0`, read with
`tools/xray-db-extract.py`):

- 28 scripts subscribe to `actor_on_first_update` (`RegisterScriptCallback`):
  gameplay (`alife_storage_manager`, `game_setup`, `itms_manager`,
  `tasks_defense`, `tasks_guide`, `tasks_pump_station_defense`,
  `axr_companions`, `gameplay_disguise`, `item_artefact`, `item_device`,
  `item_radio`, `xr_bribe`, `xr_patch`, `bind_anomaly_*`, `dynamic_news_manager`,
  `game_autosave_new`, `gamemode_ironman`, `dialogs_lostzone`, `level_environment`,
  `sound_ambient`) and HUD (`actor_status`, `actor_effects`, `ui_ctrl_lighting`,
  `ui_mm_faction_select`, `ui_pda_encyclopedia_tab`); 27 subscribe to
  `actor_on_update`.
- `get_hud()` (the engine's `CurrentGameUI()` export) is used at 61 sites in
  30 scripts; `ActorMenu.get_*` at 17 sites in 7 scripts, some unguarded
  (`pda.script:28`, `ui_pda_npc_tab.script:65-74`).
- A Lua runtime error inside a binder call is fatal in this engine build on
  both products (`lua_pcall_failed` → `xrDebug::fatal`).

So with no game UI on the server, the first unguarded HUD call in the actor's
callbacks ends the process, and guarding the engine's accessors only moves
the failure to the next unguarded script. The server cannot run the actor's
Lua binder as installed without one of:

1. **A server-side game UI object** that is inert: `CurrentGameUI()` returns a
   `CUIGameCustom` whose dialogs, indicators and menus exist as CPU objects
   and never draw. It is presentation scaffolding on the server (D2 allows
   CPU-side stand-ins for render resources, not for a player's HUD; D4 says
   each client keeps its own view actor and HUD), and it would construct the
   real `CUIActorMenu`/`CUIPdaWnd` trees from XML with their textures skipped.
2. **A server script profile**: the server does not run HUD subscribers of the
   actor callbacks. That means a content-side split (which `.script` files are
   HUD-only) or an engine-side filter on `RegisterScriptCallback`, both of
   which need a list of HUD scripts maintained against the mod.
3. **Non-fatal Lua errors on the server**, logged and counted: the failing
   subscriber aborts, the rest of that callback chain is skipped (callbacks run
   in one pcall), so gameplay subscribers after it are lost; the error list
   becomes the inventory of HUD sites to fix. Diagnostic value, not a fix.
4. **Stage 3 first**: treat the actor's Lua binder as part of the actor
   context (D4) and design the participant's script context there, keeping
   S02-T06 to the native services that do not go through the actor binder.

Options 1–2 change what the campaign server owns (D1/D2/D4 boundary), so
they need the user's decision; option 4 is the plan's own ordering if the
binder is declared actor context. Until then the GameState smoke fails at the
actor's first update with the error above, which is the true state.

## What is known to work on the server regardless

The stalkers' and monsters' binders (`xr_motivator`, `bind_monster`) run
their updates and schemes (S02-T04c/T05c); only the actor's binder reaches
HUD code. The native actor object is scheduled and processed every tick.

## Limits

  were not attempted in this session.
- The client was not rebuilt with patch 0015 (no behaviour change for it:
