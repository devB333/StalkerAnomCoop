## The bounded slice

| Operation | Supported | Refused (reason) |
|---|---|---|
| Drop an item of one's own inventory to the ground | yes (kind 6) | not in the own inventory or a quest item (14) |
| Move an item from one's own inventory into an **inventory box** or a **dead body** (an NPC's or a participant's corpse) | yes (kind 7) | the other side alive (an actor, an NPC, a trader) or not a container (13); farther than 2.5 m + 0.5 m (10); a quest item out (14) |
| Take an item from a box or a body into one's own inventory | yes (kind 7) | the item not in that container any more (9); changed owner after the client's view (12); farther than the reach (10); the engine's `CanTakeItem` (11) |
| Box to box, body to box, giving to the other player, trade | no | 13 (giving and trade: S10-T04) |
| Equip within one's own inventory (slot, belt, ruck), eat/use | not in this slice: on a client these engine events stay refused as before (S06-T04's activate-slot is the only equip action); concurrency with a transfer is tested (round 5) | — |

**Capacity:** the engine has none to enforce here: an actor's
`CInventory::CanTakeItem` has no weight limit (weight slows the actor, it
does not refuse a take; the take path checks it), and an inventory box or a
body has no capacity. The server checks `CanTakeItem` on the receiving actor.

**Revisions:** every published entity carries the lifecycle commit that last
told the clients its owner (its Spawn or its last `Reparent`). A transfer
carries the client's lifecycle cursor as the expected revision; the server
refuses `Stale` (12) when the item changed owner after it. This closes the
A-B-A case a parent check alone accepts: an item taken from a box and put
back looks the same, but a claim made from the view before those moves is
refused (round 3).

**Atomic persistence:** one `transfer` record per operation holds the whole
post-state (the item's new owner, or the ground and position). The source
container loses the item by the same engine event, so no second record is
needed and no state exists in which the item is in both or neither.

**Disconnect and conflicts:** a request is kept and re-sent with the same id
across a dropped connection (round 8); the server's stored outcome answers a
repeat. Two claims on one item resolve in the server's arrival order (the
first changes the parent synchronously, the second is refused 9).

## Deliverable

- **Server (`CoopServerHost.cpp`, `take_transfer`)**: the six phases as for
  a pickup; validation above; the record (journal kind 8 `transfer`:
  action, from entity, then the pickup layout with owner 0 = the ground);
  apply through the bridge's `GE_OWNERSHIP_REJECT` (from the source) and,
  for a container or actor, `GE_OWNERSHIP_TAKE`; at replay a ground item is
  moved to the recorded position (`GE_CHANGE_POS`) and an absent one is
  re-created there. A transfer whose container is not in the recovered world
  keeps the item on the ground at the record's position
  (`transfer-replay-owner-gone`). Failpoints `transfer:before-append|after-flush|after-apply|after-ack`.
- **Ownership invariants (`check_ownership`)**, over every ALife object
  (and the server's online table): each parent exists and lists its child
  exactly once, each listed child names that parent, no child is listed by
  two parents, no EntityId is held twice, and every online object's level
  parent equals its server parent. Logged at recovery, at every checkpoint
  and at the end (`ownership-invariants … ok=`).
- **Client (`CoopClientLink.cpp`, hook in `xrServer::Process_event`)**:
  every inventory path ends in the engine's events to the client's own
  in-process server (`GE_OWNERSHIP_REJECT` for a drop; `GE_TRADE_SELL` +
  `GE_TRADE_BUY` for a move: `move_item_from_to`, `CScriptGameObject::TransferItem`);
  before the replica refuses them (as before), the drop or the move becomes
  the intent, with the client's lifecycle cursor as the expected revision.
  A reject whose owner is an item (a grenade's throw, a launcher's rocket)
  is not a drop and is ignored. Nothing moves on the client until the
  server's `Reparent`.
- **Fixture** (server profile `transfer_race`, client script 8,
  `prepare-coop-session.py --transfer c1,c2 [--transfer-start 20]`): an
  inventory box between the players with four items, a far box (8 m) with
  one, a `sim_default_stalker_0` killed at once beside the box with a
  `medkit_army` in its body, two items in each actor (and a pistol for
  participant 2); nine rounds, each a list of steps the clients run at the
  server tick given, **through the engine's own inventory events** (the
  inventory UI's `move_item_from_to`; the drop's `GE_OWNERSHIP_REJECT`;
  `SendPickUpEvent`): 0 box race, 1 put, 2 cross, 3 stale (A-B-A), 4 drop
  race, 5 equip + move of the slot-2 item, 6 refusals, 7 corpse race,

### tr-1 (campaign-251…253 / client-153): three defects

Builds: campaign-251 (wrong header name `EntityAlive.h`), campaign-252
(`read_ref` vector type; `check_ownership` used before its declaration),
campaign-253 / client-153 built. In the run, rounds 1 (put), 2 (cross), 4
(drop and pickup), 5 (equip + slot-2 move), 6 step 1 (to the other actor,
13) and 7 (corpse race) already behaved. Defects:

1. **No item reached a box** (`box_items=65535`): items given to a box
   spawned in the same tick, still offline, are not created. Fixed: the
   fixture gives the box items once both boxes are online. Every step that
   named a box item stayed unlinked (no item to move).
2. **The invariant checker counted 39 "wrong children"** in the loaded save:
   it looked children up in ALife only, but the server's entity table holds
   online-only entities (`server_entities=1575` against 26,298 ALife
   objects). Fixed: ALife first, then the server's table; an id with no
   entity at all is counted as `dangling_child`, not a violation.
3. **The drop round is not a fair race**: the dropped item lies at the
   dropper's feet, out of the other player's reach (refused 10). The
   comparison now accepts 9 or 10 for the losing pickup in round 4.

Comparison-tool fix: operation ids are scoped per player (both clients
produced the same id in round 2), so commits are keyed by slot and id.

**Defect found by tr-11: EntityIds issued again after a restart.** The
recovery restored the identity serial only from the checkpoint
(`CoopPersistence::restore_identities` → `CampaignIdentityRegistry::restore_entities`),
so ids the crashed incarnation had issued after its checkpoint (here the
far box, entity 26387) were issued again to new objects. A client that
reconnects keeps its entity table's tombstones and refuses a reused id as
stale, so the new object never appears for it (and the identity model's
"never reused" rule, [participant identity](../participant-identity.md),
was broken). Not specific to items: any object created after a checkpoint
had the same exposure; it is a plausible cause of the S07-T05 rec-3 K4
observation. **Fix:** EntityIds are issued only below a limit the store has
made durable first: a journal record `entity-reserve` (kind 9, the new
limit) is written for every block of 4,096 before its first id is issued
(`set_entity_reserver`, `reserve_entity_block`); a checkpoint records the
reserved limit as its next id; recovery starts past the highest reservation
in the replayed journals (`recovery-identities … reserved=`). Protocol
`proto-build-41` (`st-9` 108/108, `st-10` 51/51); campaign-256 /
client-156.

The comparison tool learnt the restart's second run (`era`): the rounds the
restarted server runs must match exactly; in the first run only the round
the termination interrupted may have steps refused 8 or 5.

## Carried limits touched

- **L01**: narrowed again: drops and moves between a player and a box or a
  body reach the server as validated durable actions, from every inventory
  path. Equip moves (slot, belt, ruck), use/eat, giving to the other player
  and trade remain.
- **L36**: narrowed: drops and transfers are durable `transfer` records with
  crash tests at every failpoint. Consumption, equip state, trade, quest and
  reward effects remain.
- **K4**: the EntityId reuse fixed here is a plausible cause of the S07-T05
  rec-3 observation; not re-observed (no NPC took an item near the players
  in these runs).
- **The S07-T07 corpse** is lootable now (a dead participant's body is a
  container); exercised with an NPC's body, not a participant's.

## Limits (new)

- **Equip, use and eat stay refused on clients** (a client's slot, belt or
  ruck move and eating do nothing; the activate-slot action is the only
  equip path). Using a medkit in co-op needs its own action (S10 or a
  follow-up of S08).
- **A container created after the checkpoint is not durable**: after a
  restart its committed contents lie on the ground where the container
  was. Boxes in the level's own spawn and bodies of NPCs that died before
  the checkpoint are not affected.
- **Ammunition stacks, nested containers (a backpack in a box), weapon
  addons and partial stacks** are moved whole as one item; splitting a stack
  is not supported.
- **Item script callbacks** (`actor_on_item_take_from_box`,
  `actor_on_item_put_in_box`, the UI's own bookkeeping) run where the engine
  runs them: on the server for the server's actor processing, not on the
  requesting client before the server's answer; not audited per item.
- One host, loopback (as before).
