## What was built

**Joining with the host's code (protocol and session layer).** A player the
server's roster does not list yet joins with the host's join code: the proof
carries the player's public key and `join_mac = SHA-256("COOP-JOIN-v1" ||
code || transcript || key)`, so the code never crosses the wire and the hash
is good for one connection and one key. The server checks both, adds the
player to its roster while a slot is free and hands the entry to the campaign
server (`take_added_by_code`); a wrong code, no code on the server or no free
slot is `AuthFailed`. While the campaign server replaces its world (a travel's
reload, a new game's first level) an authenticated player gets `ServerBusy`
and retries. Details: [session authentication](../session-authentication.md).

**The campaign server.**
- Reads the host's join code from its app data (`coop-join-code.txt`, written
  by the host's menu at each Host).
- Acts on the host's choice before any level loads: `coop-create.ltx` (the
  creation screen's choices) creates a new campaign in the library (the
  S10-T06 create, factored as `session_new_campaign`), `coop-continue.txt`
  picks the most recently played campaign; either is served by a relaunch
  (exit 75 from the prepare stage: `coop-server-relaunch-at-prepare`), which
  `tools/Start-CoopServer.ps1` carries out.
- A player the code let in is appended to the roster file (its reconnects
  and the next start need no code) and bound to the free participant slot
  before its Joined; it never becomes the session's owner (the host does).
- Every binding pass starts from a fresh registry (a code-joined player
  before an in-process reload is bound again after it).

**The client's menu** (only when the app data holds `coop-menu.ltx`; without
it the client is single player as installed). New game asks:

1. *Single player (story)*: the installed flow.
2. *Host co-op: a new campaign*: the standard creation screen; its Start makes
   sure the player's key exists and is in the server's roster, writes a fresh
   join code and the choices into the server's app data, starts the server's
   launcher hidden, joins at 127.0.0.1 and shows the address (the PC's
   Tailscale address, 100.64.0.0/10, else another IPv4 address) and the code.
3. *Host co-op: continue the last campaign*: the same, with the last campaign.
4. *Join co-op*: the installed direct-IP box (Host = the address, Password =
   the join code); the player's key is made on first use (DPAPI).

Quitting the host's game stops its server (the server's stop file). A refused
join (a wrong code) is said in the HUD and ends the attempts. The menu is
built from the installed UI only (`ui_dyn_msg_box.multi_choice`,
`message_box_direct_ip`), so the content identity is unchanged.

**Kits** (`tools/make-coop-kit.py`): a host kit on this PC (a server runtime
and a client runtime whose menu can host) and a zipped client kit for a
friend's PC with `Setup-Coop.ps1` (the Anomaly 1.5.3 folder and the player's
name; it writes `fsgame.ltx`, `coop-menu.ltx`, `Start-Coop.cmd`).

## Limits found here

- **One friend per host**: two slots, and every player the code let in stays
  in the roster; a second, different friend is refused while the first stays
  listed (the roster file is the place to remove one).
- **Untested over a real network**: the friend's join used this PC's own
  Tailscale address; two PCs over Tailscale is the user's test.
- The host kit runs from this workspace (its server is the current campaign
  server build and `tools/Start-CoopServer.ps1`); packaging a host for
  another PC is S11-T05.
- The join code is shown once (a message box) and kept in the host client's
  app data `coop-host-info.txt`; it changes at every Host.
- A refused join (a wrong code) ends that attempt (a HUD message, no retry);
  New game > Join co-op can be used again. Not exercised by a run.
- The kits need an unmodified Anomaly 1.5.3 (the content identity) and the
  same build on both PCs.
