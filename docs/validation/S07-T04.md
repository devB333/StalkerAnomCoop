# S07-T04 — Recover checkpoints and committed effects safely

**Status: Completed (2026-10-23).** Engine `c57fe5b9` + patches 0001–0042;
protocol `proto-build-35`. Spec: [persistence contract](../persistence-contract.md)
§7 (recovery), §6 (reading rules), §11 (crash boundaries). Store, build and
runs shared with [S07-T02](S07-T02.md) and [S07-T03](S07-T03.md); the client
side of a restart is [S07-T05](S07-T05.md).

## Deliverable (patch 0042)

The recovery pipeline, in start order:

1. **`xrCoopServer_Prepare`** (before any service): `CoopPersistence::recover`
   runs the store's `recover` (pointer → verify G → else G−1 → journals ≥ G
   read, replay list, highest epoch and revision; `coop-tmp-*` removed). A
   fresh campaign (no pointer, no generation) loads the profile's base save,
   and a `coop-journal-0.log` of an earlier incarnation that never published
   is read for acknowledged records. Refusals stop the start with a named
   reason (`recovery-no-pointer`, `recovery-no-valid-generation`,
   `recovery-incompatible`, `recovery-journal`): never a silent reset, never
   the base save when generations exist. The epoch is `highest + 1`, written
   as the first record of this incarnation (`epoch` kind, flushed) before
   anything else. `xrCoopServer_SaveName` returns `coop-gen-<G>`.
2. **Identity service** (`coop_server_bind_roster`): the registry gets the
   saved `u16 → EntityId` map and `next_entity` (`restore_entities`); each
   saved participant's player is bound to its saved slot and slot generation
   (`restore_participant`); a roster player absent from the save is bound as
   a new participant; a saved player absent from the roster refuses the
   start (`recovery-roster-mismatch`).
3. **Native load** (unchanged engine path): every saved object's
   `PerformIDgen(saved id, object)` consumes its map entry, so the object
   continues its `EntityId` (`entities_restored = entities_saved`,
   `not_loaded = 0`).
4. **`xrCoopServer_AfterServerReady`** (new stage `coop-server-recovered`,
   between `campaign-server-ready` and the client stages): each saved actor's
   u16 must resolve to its saved `EntityId`, then it is assigned to its
   participant (`assign_participant_actor`), so the client stages' spawn
   adopts nothing by order (`recovery-actor slot=1 actor=5631 entity=26340
   … assign=none`). A mismatch stops the start (`recovery-identity-mismatch`).
5. **`xrCoopServer_Start`** (after the first 50 ticks and the identity
   check): `commit` continues from the highest revision seen; the replay list
   is applied in revision order through the adapters (`ledger` →
   `apply_ledger`, idempotent: absolute money on the slot's live actor whose
   `EntityId` matches); a record that cannot be applied stops the start
   (`recovery-replay-failed`). Then the session server is created with the
   new epoch and listens. Every join publishes a fresh generation (S07-T02).

The Stage 2 tick check (`xrCampaignLevel_ReportTicks`) accepted exactly one
actor; a serving server now accepts more (a recovered two-actor checkpoint
has both participants' actors online within the first 50 ticks).

## Validation

Harness: `tools/Run-CoopSession.ps1 -ServerKill N -ServerRestartAfter M`
terminates the server with `Process.Kill()` (`TerminateProcess`: no clean
stop, no final checkpoint) N seconds after it listened, keeps its logs in
`server-first-run/`, and starts it again in the same runtime (the same
`$game_saves$` store) M seconds later. `tools/compare-coop-recovery.py`
checks the incarnations' `coop-ledger.csv`, `coop-checkpoints.csv`,
`coop-server.log` and the clients' `coop-ledger-client.csv`.

## Limits

- **Replay needs the actor online.** `apply_ledger` sets money on the live
  actor; a participant actor not online after the first ticks fails the
  start by design (contract §7 step 7). Both actors of a two-player
  checkpoint were online in every recovery so far; a record for a
  participant whose actor was offline at the take is untested.
- Recovery takes the restart's load time (18 s here) plus the replay; no
  client can join before it. Transient state (positions, NPCs, the weather)
  rolls back to the recovered generation (contract §3, allowed).
- `death`, `respawn`, `entity` and `tombstone` records have no adapter yet
  (`recovery-replay-skipped … no-adapter-yet` would be logged): S07-T07.
- The roster must still name the saved players: a changed roster refuses
  the start rather than rebinding (contract §7 step 6).
