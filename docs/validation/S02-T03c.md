# S02-T03c — Bone and animation evaluation against a matched client capture

Recorded 2026-10-18 UTC. **Completed.** The campaign server evaluated the
neutral stalker's animated bones with no graphics device, driven by its own
clock. The normal client evaluated the same model and motion with its real
renderer. The two captures are **bit-identical**: every row matches, the maximum
difference is 0.0, and the files share one SHA-256. That exceeds the H05
tolerance of 1e-4 per matrix component.

The model was standalone, not attached to a world object. Collision, hit picking
and physics shells are S02-T03d. Parent S02-T03 stays In Progress.

## Method

Patch `0007-bone-capture.patch`
(SHA-256 `b849759d70f415f3eacf8bc6dbde7c7de2f1525e6e3740720461642a95fdd197`).

**Shared routine.** `xrEngine/CampaignBoneCapture.{h,cpp}`, `CaptureModelBones`:
1. Loads the model through `::Render->model_Create`.
2. Plays the first non-placeholder cycle, by motion slot then name. The very first
   entry, `$editor`, is a static placeholder and failed the motion check in
   `smoke-32`.
3. 50 times: advances time by one 20 ms step, runs
   `CalculateBones(TRUE)`, and writes every bone's model transform with `%.9g`.

A capture fails unless it is finite and some bone moves more than 1 mm.

Animation time is delta-based. `CKinematicsAnimated::UpdateTracks` uses
`dwTimeGlobal - Update_LastTime`, clamped to 66 ms
(`Layers/xrRender/SkeletonAnimated.cpp:626-643`). Equal step sequences therefore
give equal results.

**Server.** The `bone-capture` check in the campaign smoke runs after the frame
driver fixture. Each step is exactly one real `CCampaignServerClock` tick: an
`Advance` at the next tick's wall time, asserted to run one tick.

**Client.** `-s02-bone-capture` runs the capture at the end of
`CGamePersistent::OnAppStart`, after the materials, the game globals and the
real renderer device exist. Each step adds 20 ms to the client's device time. The
client then restores its clocks and quits. Without the flag the client is
unchanged.

**Client runtime.** `tools/Run-ClientBoneCapture.ps1 -Run <run>` uses a runtime
from `python3 tools/prepare-stage2-smoke.py <run> S02-T03c`:
- The rebuilt client executable, plus copies of the accepted runtime's DLLs,
  `user.ltx` and shader cache. The copied settings are switched to an 800×600
  window.
- The archives are read in place.
- It refuses to start if a client is already running.

The accepted source-client runtime was only read.

**Compare.** `tools/compare-bone-capture.py <server.csv> <client.csv> [1e-4]`
checks that step, bone and name match row for row, and reports the largest
absolute difference.

**Camera throttling.** View-based bone throttling is off in a CPU-only process.
`OPTIMIZE_CALCULATE_BONES` (`Layers/xrRender/SkeletonRigid.cpp:36-75`) normally
uses camera distance, screen area and the view frustum to clear `bForceExact` or
slow updates, once `g_bootComplete` is set. That flag is set only by
`CApplication`'s loading screens (`xrEngine/x_ray.cpp:2141-2185`). The block now
also requires `!CpuOnlyResources::Enabled()`, so server gameplay bones are always
exact. The client is unchanged.

The series reconstructs all 28 changed files in `builds/stage2/patch-check-08b`
(`builds/logs/patch-reconstruction-08.json`).

## Limits

- **One model, one motion.** One model, one cycle, 50 steps of 20 ms. Blending
  between motions, FX motions, partition-specific cycles and IK haven't been
  compared.
- **Standalone model.** No object, so no `spatialParent`. The throttling guard
  is in place but hasn't been exercised with a world object (S02-T03d/T05).
- **Same code on both sides.** The client capture runs the same CPU code on the
  same data. This shows the CPU-only mode doesn't change bone evaluation; it
  doesn't independently validate the animation system.
- **Client window.** The client capture briefly opens a game window on the desktop.
