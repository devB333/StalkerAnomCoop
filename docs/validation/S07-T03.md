# S07-T03 — Durable critical outcome journal

**Status: Completed (2026-10-23).** Engine `c57fe5b9` + patches 0001–0042;
protocol `proto-build-35`. Spec: [persistence contract](../persistence-contract.md)
§2, §4, §6, §10. Store library, build and runs shared with
[S07-T02](S07-T02.md) and [S07-T04](S07-T04.md).

## Deliverable

- **Journal format and storage** (`coop/store/journal.h`): one append-only
  file per checkpoint generation, header `'CJRN' schema campaign generation
  base_revision CRC`, records `length CRC sequence kind epoch tick revision
  payload`, opened with `FILE_FLAG_WRITE_THROUGH`; `JournalWriter::append`
  returns true only after `WriteFile` and `FlushFileBuffers` returned (the
  durability claim is the Windows one in contract §5; power loss untested).
  `read_journal`: a short or bad-CRC **last** record is a torn tail (dropped,
  reported); a bad record with bytes after it, a sequence gap or repeat, or a
  header mismatch is corruption (the file refused). `open_existing` continues
  after the last good record (a torn tail is overwritten). Any append
  failure marks the writer failed for good.
- **Engine side** (patch 0042): `CoopPersistence::commit` appends under the
  incarnation's epoch; `recover` appends the **`epoch` record** first thing
  (contract §7 step 4) so no two incarnations share an epoch. The
  **operation index** `(player, operation) → {outcome, reason, revision}`
  is filled from the supplemental record's operations (up to `R_G`) and the
  replayed ledger records, and published inside every supplemental record.
- **The synthetic effect**: `ActionIntent` kind 3 `ledger` (params `s32
  delta`, |delta| ≤ 1000) through the six phases in `take_ledger`
  (`CoopServerHost.cpp`): index lookup → validation (attached session, own
  participant actor dead or alive, bounded delta, store not failed) →
  resolution (`money_after = clamp(money + delta, 0, 2^31)`, revision
  `++commit`) → **durable commit** (`commit:before-append`, append+flush,
  `commit:after-flush`) → apply (`apply_ledger`: `CActor::set_money(money_after,
  true)` on the slot's live actor after checking its `EntityId`; the
  `GE_MONEY` event keeps the server entity's money in step, so the native
  save carries it) → `commit:after-apply` → the result (Accepted, `commit_id
  = revision`) → `commit:after-ack`. A known operation returns its stored
  outcome and revision without touching the world (`ledger-duplicate`).
  Rejections are not indexed (re-evaluated on retry: nothing was promised).
- **Fail closed**: a commit failure sets the store failed, the intent is
  Rejected with reason 5 `StoreFailed`, nothing is applied, every later
  critical intent gets reason 5, no publication runs again and a clean stop
  is requested (`ledger-store-failed`, `store-failed-stop`).
- **Client program 6** (`CoopClientLink.cpp`, profile `script = 6`): every
  2 s a ledger intent with the next delta of `10, −3, 7, 25, −12, 1, 40, −8,
  15, −20` and a fresh operation id seeded `(utc_ms << 16) | counter`;
  unacknowledged ones re-sent every 3 s with the same id, across connection
  ends; `coop-ledger-client.csv` rows `sent / retry / unsent / result / late`.
  Server records: `coop-ledger.csv` (`commit`, `apply`, `replay` rows).
- **Check tool**: `tools/compare-coop-recovery.py` (checks listed in its
  docstring: restored money, acknowledged-not-lost, duplicates, unique
  revisions, delta chain, checkpoints).

Contract §11 rows 3, 4, 16 and 17 are covered here (torn append, append

### Defect found by death-1 (S07-T07), fixed in campaign-233 / client-134

The `on_message` dispatch set the result's outcome only on the weapon-action
path: a **rejected** ledger or respawn intent (validation reasons 2, 3, 5,
6, 7) went out with the default outcome Accepted and commit 0, although
nothing had been committed or applied (the server log said
`intent-refused … reason=N`). The clients therefore counted a refused
operation as acknowledged (mx1-10's injected append failure: the refused
40th operation showed as `result … outcome=1 commit=0` on c1; death-1's
early respawn request "accepted"). Fixed: a non-zero reason always sets
Rejected + reason. `compare-coop-recovery.py` now fails an operation a
client saw Accepted that no incarnation committed (`acked_without_commit`),
which flags mx1-10 on the old build; the fail-closed point was re-run on the
final build as mx2-10 ([S07-T06](S07-T06.md)). The nine termination points
had no rejection (0 `intent-refused` lines) and stand.

## Limits

- Durable means `WriteFile` + `FlushFileBuffers` returned on a handle opened
  write-through: tested against process termination, not power loss or a
  device that lies about flush completion (contract §5, §12).
- An acknowledged **rejection** is not durable and not indexed: a retry
  after a restart (or in the same incarnation) is evaluated again. The plan's
  "duplicate IDs return the same outcome" holds for accepted operations,
  which are the ones that promised something.
- One durable append costs 0.3–0.9 ms on this volume (per record, on the
  simulation thread); a ledger every 2 s per player is far below any
  budget; Stage 8's rates are to be measured there.
- `apply_ledger` needs the slot's live actor online. In rec-1/rec-2 both
  participant actors were online within the first 50 ticks after a load; a
  record for an actor that is not online at replay stops the start
  (`recovery-replay-failed`), by design (contract §7 step 7).
