## What this task adds

- **The canonical item graph, compared in the stream.** Every 10 s the
  server hashes the owner of every published item (item EntityId → owner
  EntityId, 0 on the ground; sorted; FNV-1a 64) and sends the hash as a
  lifecycle event (CampaignEvent 8). Lifecycle messages reach a client in
  order on one reliable channel, so each client compares **its own replica
  at exactly the point of the stream the server hashed** (a periodic
  comparison by commit number would not work: journal records and
  lifecycle messages share one counter, and NPC churn keeps it moving). The
  server's items go to `coop-item-graph.csv`, a mismatching client's to
  `coop-item-graph-client.csv` (`CoopServerHost.cpp` `item_graph_point`,
  `CoopClientLink.cpp` `on_item_graph`).
- **The client's own inventory against the replica.** At every point the
  client also checks that its own actor's inventory (`CInventory::m_all`,
  what the inventory window lists) holds exactly the items its replica names
  as the actor's children (`missing=`, `extra=`). This is the
  "reconcile both inventories/UI from server state" check: the engine's
  inventory window is built from that list.
- **Tool:** `tools/compare-coop-item-graph.py` (checks `compared`,
  `graphs_match`, `own_inventory`; per mismatch the differing items).

## The accepted durable inventory schema

The records S08-T01…T03 rely on, as the contract defines them
([persistence contract](../persistence-contract.md) §6): `pickup` (kind 7),
`transfer` (kind 8: action, from, then the pickup layout; owner 0 = the
ground), `entity-reserve` (kind 9: the reserved EntityId limit). Each holds
absolute post-state and the item's native spawn state, and is applied by one
idempotent adapter (`apply_pickup`) at commit and at recovery; an outcome
index answers repeats with the original result after a restart.

Own inventories matched their replicas at every point of every run. The
mismatches began at the first point after each rejoin and stayed: each
client held one or two items the server no longer had (`sigaret_for_nps`
5070 in every run, `guitar_a` 26343 in inv-3), always an item the server
released right after the rejoin's watermark (inv-2: the join checkpoint at
commit 3132, the NPC smoked the cigarette at 3134).

**Defect (the root cause of K4's S07-T05 rec-3 observation):** a received
world did not reset the client's entity table. The previous world's
tombstones remained, so when the new world's online set named an entity the
table had marked dead at the same generation, `EntityTable::spawn` refused
it as recycled: the replica held the object but the table did not, its next
despawn was refused as "not live" (`stale=` counter, not logged) and the
object stayed. The same refusal hit three NPC respawns (`spawn-refused …
table=2`). **Fix:** the world received from a resync is the new baseline;
the entity table restarts from its online set (`entity-table-reset
tombstones_dropped=`). Messages of the previous connection cannot arrive
(new connection; new epoch after a restart).

### After the fix (campaign-258 / client-158)

| Run | Condition | Item graph | Fixture checks | Recovery |
|---|---|---|---|---|
| inv-7 | external kill at 100 s | c1 27/27, c2 23/23 | pass | 7 transfer records replayed |
| inv-8 | external kill at 125 s | c1 27/27, c2 24/24 | **invariants fail** (below) | 9 transfers, 1 pickup |
| inv-9 | `transfer:after-flush:3` | c1 26/26, c2 23/23 | pass | 3 transfers |
| inv-10 | pickup race, external kill at 95 s | c1 27/27, c2 26/26 | pass (all twelve pickup checks) | 4 pickups |
| inv-11 | nominal | c1 31/31, c2 28/28 | pass | — |

**inv-8:** the `recovered` invariant check found three replayed items whose
server parent was an actor while the server's own level had not attached
them yet (`level-parent … level_parent=65535`); every later check was clean
and both clients matched. Cause: the confirm queue computed the wait of a
record stamped during recovery against a wall clock restarted when serving
began, wrapped to 4,294,967,295 ms, and dropped those items as
`unconfirmed` on the first tick, so the `recovered` check ran before the
level caught up. **Fix:** the wait is never negative (`waited`), so a replayed
item stays "in flight" until its level object is confirmed.

## Limits

- The item graph compares **published (online) items** only; offline items
  inside offline containers are compared through the checkpoint the client
  loads, not point by point.
- The inventory window itself is not inspected (unattended runs have no
  UI); its data (`CInventory::m_all`) is.
- One host, loopback.
