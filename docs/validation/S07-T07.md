# S07-T07 — Respawn a dead player with a lootable corpse

**Status: Completed (2026-10-23).** Engine `c57fe5b9` + patches 0001–0042;
protocol `proto-build-35` (action kind 4 `respawn`, `CampaignEvent` kind 5
`rejoin`, no wire change). Added at G06 (user decision 2): a dead player
continues after a prompt; the old body stays in the world with its
inventory, as the installed Azazel mode leaves one (its `stalker_azazel`
mimic, `gamemode_azazel.script` 262-286; the engine's `CActor::Die`,
`Actor.cpp:894`, drops the active-slot item beside the body and moves the
rest to the bag). Spec: [persistence contract](../persistence-contract.md) §9.

## Deliverable (patch 0042)

- **Prompt (client, `CoopClientLink.cpp`):** 3 s after its own death the
  client prints the prompt into the HUD message log
  (`CUIGameCustom::CommonMessageOut`: "You died. Press the USE key to
  respawn at your last checkpoint.") and logs `respawn-prompt`. The use
  key, caught in `CLevel::IR_OnKeyboardPress` before the level's handling
  (`campaign::coop_client_key_press`, only while dead and prompted), sends
  the respawn intent; the unattended driver sends it `auto_respawn` seconds
  after the death (profile key, `prepare-coop-session.py --auto-respawn N`)
  and, once, an early request 20 s into the world while alive (expected
  refused). The request (`ActionIntent` kind 4, no params, id tagged
  `0x7e5f` + UTC ms) is re-sent every 3 s until a result, across a
  reconnect.
- **Operation (server, `take_respawn`):** index lookup → validate (attached
  session, the slot's actor exists and is **dead**: an alive actor gets
  reason 6; no params) → resolve the point: the slot's position in the
  latest published generation when it holds this actor, else the last
  position the server saw the actor alive (tracked every tick), else beside
  the corpse; the level vertex and the graph vertex; a reserved `EntityId`
  → durable `respawn` record (slot, player, operation, old entity, new
  entity, position, vertex, graph) → apply: `create_participant_actor`
  (the S03-T03 path: a genuine actor from the `actor` section with its
  supplies, `start_position_filled` set) carrying the reserved entity id,
  the slot's actor binding moved from the corpse to the new actor
  (`bind_actor`), the corpse left as it is → `ActionResult` Accepted →
  `CampaignEvent` 5 `rejoin` to that player.
- **Rejoin (client):** on the event the client leaves its world and
  reconnects at once (the S07-T05 path); the join streams a world whose
  slot actor is the new one, so its player entity is the new actor by
  construction and the corpse arrives as any other dead actor.
- **Recovery:** the `respawn` record is replayed by `apply_respawn`
  (idempotent: if the slot already holds the recorded entity or the
  checkpoint already contains it, nothing is spawned; else the actor is
  spawned with the recorded entity and bound); the participant's `death`
  record (S07-T06) precedes it in the journal.
- Failpoints `respawn:before-append`, `respawn:after-commit`,
  `respawn:after-apply`, `respawn:after-ack`.

### death-1 (campaign-232 / client-133): three defects

Both players died (the boar killed participant 2 at 20 s of the program;
a bandit killed participant 1 at 65 s): `death-committed revision=1555
slot=1 … killer=26362 (the boar)`, `revision=1557 slot=255 (the boar, killer
entity 1 = participant 1)`, `revision=1570 slot=0 … killer=25839`, and 20
NPC deaths. Both clients prompted 3 s after their death. Then:

1. **The prompt froze the clients.** `CUIGameCustom::CommonMessageOut`
   writes to the HUD message window's game log, which single-player's game
   UI does not create; the fault ended in the crash dialog and both clients
   had to be killed. Fixed: the prompt goes through the installed scripts'
   `actor_menu.set_msg` (the Azazel mode's own message path).
2. **The early request was "accepted".** The server refused it
   (`intent-refused … kind=4 reason=6`) but the result carried the default
   outcome (the S07-T03 dispatch defect, fixed).
3. **The restart refused a dead actor 0.** With both actors dead at the
   clean-stop generation 11, `xrCampaignLevel_ReportTicks` failed
   (`actor->g_Alive()` required) and the restart exited 12. Fixed: a serving
   server accepts a dead participant actor from the checkpoint.

## Limits

- **Respawn loop in a hostile spot.** The respawn point is the last
  generation's position for the actor (the death spot when the generation
  was taken there), so a player killed by NPCs that stay respawns among them
  and dies again (death-2: 19 respawns in 7 minutes). G07 decision 2 asks
  whether to add a safe-point rule (nearest level changer or smart terrain
  of a friendly faction) before Stage 8.
- After an accepted respawn the driver may send one more auto request before
  the rejoin takes effect (`respawn-request why=auto … sent=0`: the
  connection is already closing); harmless, not sent.
- Looting the corpse needs inventory transfers (S08-T02): its items are
  visible and stay, but cannot be taken (plan.md S07-T07 risk).
- The new actor carries the `actor` section's supplies (the faction's
  new-game kit as the installed scripts give it is `start_position_filled`
  logic plus loadout scripts that run for `db.actor` only; a second
  participant's actor has no binder: L32), not the dead actor's equipment.
- `alife().graph().actor()` stays the first spawned actor's server entity
  (the corpse after participant 1 respawns); the lookups that use it for a
  graph vertex or an anchor keep working from the corpse's position.
- The prompt is a HUD log line, not a dialog; a "reconnecting" screen is
  not shown during the rejoin (the main menu is).
