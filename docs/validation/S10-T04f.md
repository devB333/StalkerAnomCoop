## What was built

**Where Anomaly's upgrade window really is (T04f-5).** The engine's
mechanic flag (`mechanic_mode`) is commented out of the installed character
descriptions, so the talk window never shows the engine's upgrade button;
the player reaches repairs and upgrades through the dialogue phrase whose
action is `dialogs.npc_is_tech` → `npc:start_upgrade(db.actor)` (traders:
`npc_is_trader` → `start_trade`), and the window that opens is the installed
**Lua** inventory UI (`ui_inventory.script`, repair mode), not
`CUIActorMenu`: the engine's `StartUpgrade`/`StartTrade` call the script hook
`actor_menu_inventory.CUIActorMenu_OnMode_*`, which opens the Lua window and
returns true. A mechanic is a section of `misc\stalkers_upgrade_info.ltx`
(the script's `param_ini`). In co-op the dialogue runs on the server
(S10-T04a), so `talk_quest_action` takes those two phrase actions over
(`talk-upgrade` / `talk-trade` log lines) and opens the player's session
(`upgrade_open_for` / `trade_open_for`, also used by the intents); the
server's mechanic check is the flag or the ini section.

**The upgrade session (T04f-1).** The remote talk window's upgrade button
(when a character does carry `mechanic_mode`) sends the upgrade-open intent
(21) for the mechanic the player talks to. The server checks the talk and
the mechanic, opens the session (`PlayerLink::upgrade_npc`, inside the
talk: a talk close closes it) and sends the **upgrade table** (CampaignEvent
16): for every item of the player's inventory that has an upgrade scheme,
whether this mechanic upgrades it (the installed
`inventory_upgrades.can_upgrade_item`) and, for each upgrade of the item's
root, `Upgrade::can_install` and the price (`get_upgrade_cost`). It runs in
the player's context with the mechanic set as the script speaker
(`UpgradeSpeaker`: the `used_npc_id` event a USE sets in single player, which
`get_speaker()` reads; restored after). The client opens the native upgrade
window when the last part arrives (`CUIGameSP::StartUpgrade`);
`CUIActorMenu::CanUpgradeItem` and `Upgrade::can_install` read the table on a
co-op client, so the cells show the server's states.

**Install and repair (T04f-3).** A cell's confirmed click reaches
`Manager::upgrade_install` (the Lua window's `obj:install_upgrade`, the
engine window's `OnMesBoxYes`), which on a co-op client sends the upgrade
intent (22, op 1, the upgrade id) instead of installing; the Lua window's
repair (`inventory_upgrades.effect_repair_item` then `obj:set_condition`)
reaches `CScriptGameObject::SetCondition`, which sends op 2 while an
upgrade session is open and the value is a repair; the engine window's
`RepairEffect_CurItem` does the same. The Lua window's `give_money` calls
are dropped while a session is open (the purse is the server's) and its
lending `transfer_item` to the mechanic too (the server lends, T04f-2); its
`transfer_item` between the player and the trader while a **trade** is open
becomes the trade intent (one per click, T04f-6). When the table opens the
Lua window the client sets `used_npc_id` to the mechanic, so the window's
own `precondition_functor_a` evaluation (through `get_speaker()`) sees him.
The window's lists are nudged (`ui_inventory.GUI:On_Item_Update`) after an
installed upgrade, a repaired condition or a trade refresh; the session
ends when the Lua window (or the engine menu) is no longer shown for 1.5 s
after it opened, or with the talk. The server validates again (the
open session, the item in the player's own inventory, `can_upgrade_item`,
`can_install`, the price; a repair: condition below 0.99, the installed
`can_repair_item`, the script's price formula), journals one **`upgrade`
record** (`kRecordUpgrade` 15: item, op, upgrade id, price, purse after),
then applies through the engine's own path in the player's context: op 1
`Manager::upgrade_install` (the effect functor charges `db.actor`), the
server entity's upgrade list (for the checkpoint and a joining client's
spawn) and `effect_upgrade_item` (the mechanic feature, T04f-2); op 2
`effect_repair_item` and `SetCondition(1)`. The purse is set to the recorded
value. **CampaignEvent 17** tells every client to install the same upgrade
on its copy in loading mode (no charge); the window refreshes
(`CoopUpgradeRefresh`: the item's new grid, the states, the condition
bars); the condition reaches the client in the layout (T04c-7) and the money
with the survival event. Recovery replays the record: the upgrade installed
again on the restored item (loading mode) or the condition set, the purse
set (`upgrade-replayed`).

**Fixture (`--upgrade c1,c2`, profile `upgrade_party`, server-driven;
`CoopServerHost.cpp upgrade_fixtures`).** Both players placed beside the
nearest online mechanic; player 1 gets 50000 RU and the mechanic's tier
infos (party-shared, T04b). Player 1 talks and opens the session (player 2's
talk start must be refused busy, 33), installs the first installable upgrade
of the first item that has one, wears its first weapon to 0.5 and repairs
it, closes. After the external kill the restart replays both records.
`compare-coop-upgrade.py` checks the seven points in its header.

## Limits found here

- The client's tooltip shows the base price (T04f-4); the Lua window's
  own states come from its local evaluation (the pushed purse, the mirrored
  infos, the client copy's condition), the server's table binds the result.
- The mechanic feature (lending) follows the server's option (T04f-2); the
  lent item's return through the mechanic's dialogue was not exercised by
  the fixture.
- The fixture is server-driven: it proves the server's session, the
  records and the recovery, not the Lua window's clicks; the window path is
  the user's hands-on (upgrade, repair, and the trade window of T04c-1).
- The Lua window shows a bought or sold item in its old list until the
  server's move arrives and the nudge runs (tens of milliseconds).
