## Part 1: the mouse and windowed co-op clients

**Request (user, 2026-10-22):** "make the builds so if I alt tab I can move the
mouse around and change the position of the windows."

**What the engine did** (`xrEngine/device.cpp`, `CRenderDevice::OnWM_Activate`,
the `g_always_active` branch the co-op clients use): on any activation it hid
the cursor, clipped it to the window's client area (`ClipCursor`) and acquired
DirectInput, and the level re-centres the cursor on every mouse move
(`Level_input.cpp:136-140`). A click on a game window's **title bar** activates
the window, so the cursor was at once confined below the title bar and the
window could not be dragged; the only way out was alt-tab. Input also
re-acquires the mouse by itself every frame (`Xr_input.cpp`, `MouseUpdate`).
Alt-tab itself already released the cursor (deactivation: show, unclip,
unacquire). `SC_MOVE` in `WM_SYSCOMMAND` is swallowed, but a title-bar drag is
`SC_MOVE | HTCAPTION` and never matched that case, so it was not the cause.
The two co-op clients also open at the same place, one on top of the other.

**Change (patch 0037)**, `device.h`, `device.cpp`, `Device_wndproc.cpp`,
`Xr_input.cpp`:
- A windowed, always-active window activated by a click outside its client
  area (title bar or frame) does not take the mouse: the cursor stays visible
  and free, input stays unacquired (`b_cursor_capture_pending`), and the window
  can be dragged.
- A click inside it then takes the mouse as before (`WM_LBUTTONDOWN`).
- Alt-tab into the window and clicks inside it capture at once, as before.
- The window menu's Move (`SC_MOVE`) works in windowed mode.
- Fullscreen, borderless, and windows without `g_always_active` are unchanged.

**Check** (`tools/Test-WindowCapture.ps1`, new; it drives the real mouse for
about 10 s). It raises a client window of a running session, clicks inside it,
moves the focus away as alt-tab does, drags the window by its title bar 160 ×
90 px, then clicks inside it again.

| Step | Expected | window-capture-3 (campaign-212 / client-114) |
|---|---|---|
| click inside | window has focus and the mouse | clip = client area (568,271–1352,832) |
| focus leaves | cursor free | no clip; cursor reached (10,10) |
| title-bar click | window active, mouse free | foreground, no clip |
| drag | window moves | 560,240 → 720,330 (exactly 160 × 90) |
| click inside | mouse taken again | clip = the moved client area (728,361–1512,922) |

`builds/logs/S06-T07/window-capture-3.json`; session `win-1` (two idle clients,
Cordon). window-capture-1 and window-capture-2 are invalid: the game windows
were behind the user's maximised terminal, so the clicks landed there (the
check now raises the window first).

**Not tested:** the old build with the same check (only reasoned from the
code); multi-monitor setups; borderless and fullscreen (unchanged code paths).

## Part 2: a player's own weapon actions and the other player's weapon

**Report (user, 2026-10-22, after a hands-on demo):** "after a little bit
friendly fire stopped working, it worked initially but broke down" and
"Player 1 cannot see player 2 with their gun out".

**What the logs showed** (`demo-4`, clients' `coop-combat-client.csv`, which
records each actor's local and server slot, rounds and shots):
- Only the fire key reached the server from a real player. Reload and weapon
  switching were local: player 2's server pistol fired its 8 rounds (server
  rounds 0 at 166 s), then player 2 reloaded only on their own screen (local
  8, server 0), so every later shot existed only locally. Player 1 drew the
  pistol locally at 113 s and 191 s and fired 8 local rounds, but the server
  had player 1's actor holstered all session (server slot 0); none of those
  shots existed. `send_action` was only called by the test programs.
- On a client the other player's weapon never left `eHidden`:
  `CHudItem::SwitchState` changes a state only by sending
  `GE_WPN_STATE_CHANGE` from a local object and waiting for its echo; the
  other player's items are remote on a client, so its pistol was never drawn
  even while the server had it out.
- The arming fixture gave the new actor (player 2) its pistol into empty
  hands, which drew it; the saved actor (player 1) already had one in its
  slot, holstered. The players started differently.

**Changes (patch 0038):**
- `CoopClientLink.cpp`, `forward_player_actions`: each frame the client
  compares the slot its own actor is switching to (`GetNextActiveSlot`) with
  the slot last asked of or reported by the server, and sends the same
  activate-slot action the programs use; a reload starting on its own weapon
  sends the reload action. A slot the server set is not sent back. Not while
  the combat or encounter program (which send their own actions) runs.
  Counters `player_slot_actions` and `player_reload_actions`.
- `HudItem.cpp`, `CHudItem::SwitchState`: on a co-op client, an item carried
  by a remote participant actor changes state locally (presentation), so the
  other player's drawn weapon shows. NPC weapons are unchanged.
- `CoopServerHost.cpp`: the arming fixture puts each pistol away once it is in
  slot 2, so both players start empty-handed.

**Checks** (`tools/Send-ClientActions.ps1`, new: drives a client window with
real key and mouse input; the walk program, which faces the other player and
takes screenshots at 3.5 s and 23.5 s):

Player 2's `2` holstered its already-drawn pistol (the fixture difference) | player 2 sees player 1 with arms raised in the pistol pose; player 1 sees player 2 (holstered) with arms down |

  caused by this part (no weapon or actor code is involved); it appears when
