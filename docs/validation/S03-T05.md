## What the installed scripts and the engine do (source)

Installed scripts from `builds/build_2/test-install/source-client/db/configs/scripts.db0`
(extracted with `tools/xray-db-extract.py`, 413 scripts) plus the runtime
`gamedata/scripts`.

- "The player" has four forms in the installed Lua: `db.actor` (3,228 uses in
  245 scripts; a field of the `db` namespace set by `db.add_actor` from the
  actor binder, `db.script:102-112`), the engine id 0 (`AC_ID = 0`,
  `_g.script:51`, 290 uses in 76 scripts; `has_alife_info(id)` is
  `alife():has_info(0, id)`, `_g.script:2533`, 638 uses), `alife():actor()`
  (58) and the story object `"actor"` (20).
- The quest path the fixtures use touches all the per-actor ones:
  `dialogs.who_is_npc` picks the NPC by `first_speaker:id() == AC_ID`
  (`dialogs.script:1869`); preconditions are condlists checked against
  `db.actor:has_info` (`xr_logic.script:371-398`); `setup_generic_fetch_task`
  stores the fetch item in `db.actor`'s portable store and needs a talking
  partner from `get_speaker(true)` (`tasks_fetch.script:489-530`,
  `_g.script:2494`); the Lua task check runs from the actor binder's update for
  every task (`task_manager.script:104-119`, `task_objects.script:173`);
  completion runs the task's `on_complete` from `task_callback`
  (`task_manager.script:183`), registered by the binder on its own actor
  (`bind_stalker.script:157`); the money reward is paid one second later by a
  time event that reads `db.actor` when it fires (`tasks_fetch.script:146-236`,
  `CreateTimeEvent`, `_g.script:339`); goodwill goes to `db.actor`
  (`xr_effects.script:1295-1303`).
- Engine: `CGameTask::ChangeStateCallback` and the task info checks used
  `sole_participant_actor` (S03-T02), refused with two actors, so a second
  participant's task could never complete; the native task manager is one per
  level and does not record who received a task (`GametaskManager.cpp:94-132`);
  news and talk messages went to "the" actor; `CActor::RunTalkDialog` shows the
  talk window through the game UI (`actor_communication.cpp:125`).
- Namespaces are tables whose metatable `__index` is `_G`
  (`xrServerEntities/script_storage.cpp:43-52`), and `_G`'s own metatable is
  the auto-loader (`script_engine.cpp:353-363`); luabind Lua classes look
  methods up on the class table at call time (`luabind/src/class_rep.cpp:1196-1255`),
  so both `db.actor`/`AC_ID` and a class method can be resolved per context
  without editing the installed files.

## Acceptance

- **Native and Lua fixture identifies the correct actor/party:** the probe
  rows (slot, generation, party, origin, actor, `db.actor`, `AC_ID`) for each
  participant and the per-actor effects; both quests' owners, rewards,
  goodwill, info portions and items.
- **No arbitrary global fallback:** outside a context the contract's lookups
  return nothing (counted); refused contexts enter nothing; a captured context
  is re-authorized (unit fixture: a released participant's capture is refused,
  `unknown-participant`); an owned task whose owner is gone does not get its
  callback (logged). The remaining single-player behaviour of the installed
  scripts outside a context is named, bounded and counted (audit), not hidden.
- **Both contexts coexist:** nested contexts, both deferred events, and the
  two quests open at once, each checked, completed and rewarded in its own
  owner's context.
- **G02 carried input:** the S02-T06e quest now runs with participant 1's
  explicit context; the same installed quest line ran for participant 2's own
  actor; the talk window is a `DialogOpen`/`DialogClose` presentation.

## Limits

- **Installed scripts outside a context still use actor 0** (`db.actor`, id 0):
  NPC logic, meet/talk availability, disguise, warfare, the binder's own
  updates (audit above). Converting them is bounded batches in S08/S10.
  Observed consequence: the giver's talk availability is decided against
  actor 0 (`xr_meet.process_npc_usability`); the fixture places actor 0 beside
  him too.
- **Not remapped:** `has_alife_info` / `alife():has_info(0, …)`,
  `alife():actor()`, the story object. Inside participant 2's context an info
  portion given through `db.actor` goes to actor 2 while `has_alife_info`
  still reads actor 0 (tier-1 for actor 30464 is invisible to
  `has_alife_info`). Which info portions are party state is S08.
- **The giver's talk was disabled by his own schedule in smoke-135**
  (`talk_enabled=0`, walking away); the final fixture enables his talk before
  each dialogue if needed (as the installed `force_all_talk` option would) and
  records `talk_enabled` per dialogue: in smoke-136 it was already enabled
  every time.
- **Per-giver lists are not per participant:** `axr_task_manager`'s offered
  and finished lists are keyed by NPC; the fixture sequences the two turn-ins
  so the second task is not yet at its complete stage when the first is
  turned in. A party/owner filter is S08.
- **Ownership and captured contexts are not saved:** a checkpoint-loaded task
  has no owner and runs outside any context (8,008 unowned task updates and
  checks over the run: the save's own task and the S02-T06e task after their
  restores); actor 2's portable store and its
  `db.storage` entry are memory only. Stage 7.
- **Same task id twice:** participant 2's `task_1` is a second native entry
  beside participant 1's completed one; lookups use the in-progress one.
- Presentation outboxes are recorded, not delivered (Stage 4); out-of-context
  effectors and news are dropped (206, counted).
- The phrase-script scopes (`CDialogScriptHelper`) and `RunTalkDialog`'s server
  branch are compile- and regression-checked only: the fixtures call the
  dialogue functions directly, as S02-T06e did, not through `CPhraseDialog`.
- The time-event key `0`/`"delay_reward"` is global: two participants
  completing fetch tasks within one second would collide in the installed
  queue (S08).
- The G01 waivers and the G02 carried limits are unchanged; the S03-T04 open
  item (server AI vision has no light) is unaffected.
