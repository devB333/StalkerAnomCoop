## Question

Plan.md S03-T03: use the controlled server harness to create two genuine
campaign actors; bind identities and independent input/control contexts;
verify condition, equipment, inventory containers, death and lifecycle
independently. **Acceptance:** both are participants, independently
addressable with distinct state; destroying one does not invalidate the
other or global services. **Validation:** scripted native commands exercise
each actor, lifecycle/slot reuse and save-ready identity mapping.

## What the engine does (source)

- An actor moves by input only when it is the process's one control entity:
  `CActor::shedule_Update` runs `g_cl_CheckControls` (from `mstate_wishful`,
  set by the actor's own `IR_OnKeyboardHold/Press/Release`,
  `ActorInput.cpp:351-430`), `g_cl_Orientate` (from the actor's own camera
  yaw, `Actor_Movement.cpp:499`) and `g_Physics` only for
  `Level().CurrentControlEntity() == this` (`Actor.cpp:1825` before the
  change); every other actor is interpolated from network updates. The
  campaign server adopts no control entity (S02-T05d), so no actor on it
  moved by input before this task.
- A second actor is a genuine `CSE_ALifeCreatureActor` from the `actor`
  section through the native spawn (`CALifeSimulatorBase::spawn_item`,
  `alife_simulator_base.cpp:98`, the call behind `alife():create`); the
  switch manager brings it online (`alife_switch_manager.cpp:46-66`,
  `xrServer::Process_spawn`, `CActor::net_Spawn`). The ALife actor stays the
  `M_SPAWN_OBJECT_ASPLAYER` entity (`alife_graph_registry.cpp:53-57`); the
  global `g_actor` is set only for that flag (`Actor_Network.cpp:536`).
- The installed `actor` section binds `bind_stalker.actor_init`
  (`class_registrator.script:24`), whose `actor_binder` sets `db.actor` and
  resets and finalizes the weather, surge and psi-storm managers
  (`bind_stalker.script:29-142`, `db.script:102-112`); its server class
  `se_actor` reads its own state bytes only `if db.actor == nil`
  (`se_actor.script:40-54`); `_G.CActor__BeforeHitCallback`
  (`_g.script:1221`) ignores hits for 7 s after the binder's first update
  (`bind_stalker_ext.script:74-76`) and hits from any stalker or actor
  friendly to `db.actor` (`IsStalker`, `_g.script:2838`, includes actors).

## Acceptance

- **Both are participants, independently addressable with distinct
  state:** shown by the identity, condition, inventory and control phases
  above (two players, two entity ids, each actor resolved only by its own
  participant, hit, equipped and driven without touching the other).
- **Destroying one does not invalidate the other or global services:**
  the death and lifecycle phases (actor 1, ALife, scheduler, script process,
  identity audit intact; the single-actor accessors recover).
- **Lifecycle/slot reuse and save-ready identity mapping:** the third
  actor under the same participant with a new entity id; the map rows list
  slot, generation, state, player, entity, engine key and the entity id
  stored on the server entity for both participants (persistence of the
  mapping is Stage 7).

## Limits

- The second actor has no Lua binder on the server by rule (S03-T05 owns
  the participant script context): the installed scripts' `db.actor`,
  weather/surge managers, hit gates, artefact immunities and news all
  assume one actor (recorded in the inventory).
- Hits sourced from an actor are dropped by the installed pre-hit callback
  as friendly fire against `db.actor`; the fixture hits from an anomaly
  zone. Friendly-fire policy is Stage 6.
- God mode (`psActorFlags`) is process-wide; the fixture clears and
  restores it.
- The ALife switch manager still measures from the ALife actor alone; the
  second actor stays within 3 m (activation union is S03-T04).
- `g_spawn_state_resyncs` is 13516 over the run before the fixture: every
  `smart_terrain` read at save load is 1 byte short in its Lua `STATE_Read`
  (harmless there, the save loader frames each object; logged 16 times).
  The resync now also neutralises it on the live spawn path; the script
  asymmetry itself is an installed-scripts matter (S03-T05).
- The hearing stage's `npc_walk_events=0` variation recurred twice in a row
  (smoke-114/115) on an unrelated build; S03-T04 owns the footstep cause.
- Input is the harness's; the client's intent protocol is Stage 4. The
  walk is a held forward command; no look input was exercised.
- The G01 waivers and the G02 carried limits are unchanged.
