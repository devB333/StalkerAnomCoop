# S02-T04c — Objects, AI, ALife and the server activity policy

Recorded 2026-10-18 UTC. **Completed.** The campaign server now prioritises
simulation from activity anchors (the online actors) instead of the camera,
and on the loaded level (S02-T05d), with no graphics device, objects, the
scheduler, the stalkers' planners and ALife all advance from the server ticks:
the GameState smoke (smoke-57) **passed** with the new stage
`campaign-activity-passed` (H04). The normal client built from the same
source (client-17) ran the same fixture on the same save (`capture-06`) and
also passed it; the comparison agrees on every rule except one asserted ALife
parameter (`objects_per_update` 65534 on the server, 20 on the client), which
traces to the actor's Lua binder and is recorded as a finding for S02-T06.

## What the camera decided (source)

- **Crows.** `CObjectList::Update` updates only the *crows* each frame
  (`xrEngine/xr_object_list.cpp:198-266`); in single player
  `CLevel::OnFrame` keeps `rsDisableObjectsAsCrows` off (`xrGame/Level.cpp:988-991`).
  `CObject::UpdateCL` re-nominates an object as a crow when its parent is the
  view entity, when it is `AlwaysTheCrow`, when it is within 30 m of
  `Device.vCameraPosition`, or within 60 m and rendered in the last two frames
  (`xrEngine/xr_object.cpp:396-409`, `CROW_RADIUS`/`CROW_RADIUS2` in
  `xr_object.h:20-21`). A scheduled update also makes the object a crow
  (`xr_object.cpp:404-408`), so a distant object gets one `UpdateCL` per
  scheduled update.
- **Scheduling interval.** `CSheduler::ProcessStep` spaces an object's
  `shedule_Update` between `t_min` and `(1000 + t_max) / 2` by
  `shedule_Scale()` (`xrEngine/xrSheduler.cpp:356-361`), which is the camera
  distance over 200 m (`xr_object.h:103`). Stalkers and monsters use
  `t_min = 100`, `t_max = 250` (`xrGame/CustomMonster.cpp:830-831`), the ALife
  manager a fixed 0.5 (`xrGame/alife_update_manager.cpp:87-90`).
- **On the server before this task** the view entity was null, so the first
  branch (`Parent == CurrentViewEntity()`, both null) made every top-level
  object a crow, and the scale used the distance to the level origin. That was
  the arbitrary camera-derived policy to replace.
- Other `vCameraPosition` and `CurrentEntity()` users in the game module are
  presentation (tracers, step sounds, detector effects) or actor-context
  items for Stage 3 (monster `CurrentEntity()` targets, actor use/pick);
  none decides simulation priority.

## What AI and ALife do per tick (source)

- `CAI_Stalker::shedule_Update` (`xrGame/ai/stalker/ai_stalker.cpp:1129-1250`):
  object handler, vision, memory, then `Think()` (planner) or
  `ProcessScripts()` under script control, `m_dwLastUpdateTime` set either
  way. `CBaseMonster::shedule_Update` (`base_monster.cpp:363-393`).
- `CALifeUpdateManager::shedule_Update` (`alife_update_manager.cpp:118-140`):
  the first run inline, later runs queued on `seqParallel` (`mtALife` is on by
  default, `console_commands.cpp:315-318`), which the campaign driver runs
  serially each tick (S02-T04a). `update()` = `update_switch()` over this
  level's registry (`CSwitchPredicate`, `alife_update_manager.cpp:20-52`) and
  `update_scheduled()` over the offline schedule registry
  (`alife_schedule_registry_inline.h:24-31`, `objects_per_update` per cycle).
- Switching: `CSE_ALifeDynamicObject::try_switch_online/offline`
  (`alife_dynamic_object.cpp:133-181`) compare the distance to the ALife
  actor with `online_distance = switch_distance * (1 - factor)` and
  `offline_distance = switch_distance * (1 + factor)`
  (`alife_switch_manager_inline.h:35-40`). Offline scheduled work is
  `CSE_ALifeMonsterAbstract::update` → `brain().update()`
  (`alife_monster_abstract.cpp:55-60`, `xrServerEntities/alife_monster_brain.cpp:156-176`).
- ALife game time is `m_game_time + factor * (Device.dwTimeGlobal - start)`
  (`alife_time_manager_inline.h:23-26`), so it follows the server clock.
- Script-controlled movement: `CScriptEntity::AddAction` →
  `ProcessScripts` → `bfAssignMovement` sets the level path destination
  (`script_entity.cpp:177-195, 267-330, 490-600`), and
  `CAI_Stalker::bfAssignMovement` applies body/movement state and runs the
  movement manager (`ai_stalker_script_entity.cpp:57-76`). This is the path
  Lua's `object:command()` uses.

**Engine, `xrEngine/xr_object.{h,cpp}`:** `SActivityPolicy g_activity_policy`
(`enabled`, `crow_radius`, `anchors`). When enabled, `CObject::UpdateCL`
nominates crows by `AlwaysTheCrow()` or nearest-anchor distance below
`crow_radius` (60 m: the client's visible-object radius, since the server has
no visibility test), and `shedule_Scale()` is nearest-anchor distance / 200.
Disabled (the client), nothing changes. `xrEngine/xrSheduler.{h,cpp}`:
`CSheduler::dwUpdated` counts `shedule_Update` calls per `Update`.

**Game module:** `xrGame/CampaignActivityPolicy.h` and
`CampaignServerStart.cpp`: the policy is enabled when the campaign level
starts and disabled when it stops; `CampaignActivityRefreshAnchors()` sets one
anchor per alive `CActor` on the level, called from `CLevel::OnFrame` right
after `ProcessGameEvents` for the campaign server (`Level.cpp`), so an actor
spawned that frame already counts. With the saved actor that is one anchor; a
second participant (Stage 3) adds its own (R11, participant union).

**Fixture, `xrGame/CampaignActivityCapture.{h,cpp}`** (rows documented in the
header), shared by the server and the client (`-s02-activity-capture`):
- **Observe** (default 10 s, `-s02-activity-observe-ms`): after every tick a
  `tick` row with frame, time, ALife game time, object-list counters
  (objects, active, crows, updated), the scheduler dispatch count, physics
  steps, online count on this level, switches since the previous tick
  (`switch` rows with the distance to the ALife actor), offline schedule
  registry size and how many of its counters advanced; an `npc` row for the
  identified stalker (`-s02-activity-npc`, default 19409,
  `esc_2_12_stalker_fanat`, 0.6 m from the saved actor): scheduled updates
  (changes of `m_dwLastUpdateTime`), planner and object-handler current
  action ids, path type, destination vertex, movement/body/mental state,
  position, speed.
- **Walk** (budget 30 s, `-s02-activity-walk-ms`): the destination is the
  first accessible level vertex found by breadth-first search from the
  stalker's vertex at least `-s02-activity-distance` (10 m) away, so it is
  reachable by construction; the stalker is taken under script control
  (`SetScriptControl`), given one `CScriptMovementAction` (stand, walk, smooth
  path) and released on arrival (< 1 m) or when the budget ends.
- **Pass rule:** the stalker stays alive; ≥ 10 scheduled updates while
  observing; its planner had a current action; scheduler dispatches and object
  updates were counted; ALife switched at least one object; at least one
  offline scheduled counter advanced; game time advanced by
  `sim_ms × time_factor` within 10 %; the walk was commanded, the stalker
  arrived and walked ≥ 0.8 of the destination distance; all values finite.

**Server:** after `campaign-physics-passed`, `xrEngine/x_ray.cpp` begins the

## Findings

- **The ALife manager runs every tick on this content** (`schedule_min` and
  `schedule_max` are 1 in the content's `alife.ltx`), so offline scheduled
  work is a per-tick cost: ~91 brain updates per 20 ms tick on the server
  here. Record for R11 (CPU load) before Stage 3 adds a second anchor.
- **`objects_per_update` is 65534 on the server and 20 on the client, and
  the actor's Lua binder first update did not run on the server.** The
  content's `alife.ltx` says `objects_per_update = 20` (read by
  `CALifeUpdateManager` at `alife_update_manager.cpp:71`). Lua raises it:
  `bind_stalker.script` `actor_binder:reinit()` line 200 calls
  `alife():set_objects_per_update(65534)` when the actor spawns ("to force all
  of alife to spawn and update at least once"), and `actor_binder:update()`
  lines 236–240, in its first-update block, queues
  `set_objects_per_update(20)` as a one-second time event. The client log has
  that block's `collectgarbage before=` print (line 2032 of
  `run-capture-06/client.log`); the smoke-57 server log has none, and no Lua
  error mentions the actor. So on the server the actor binder's `update`
  (reached through `CActor::shedule_Update` → `CGameObject::shedule_Update` →
  `CScriptBinder::shedule_Update`, guarded only by `g_dedicated_server`,
  `GameObject.cpp:1091`) never ran its first-update block, ALife kept
  processing every offline object each tick, and whatever else that block
  does (info portions, PDA objects, the active slot) is also missing. The
  scripts were read with the new `tools/xray-db-extract.py` from
  `db/configs/scripts.db0` and `configs.db0`. Isolating the cause (the actor's
  scheduled update, the binder, or the time-event pump `level.add_call` →
  `ProcessEventQueue`) is S02-T06 work (Lua execution); the compare tool keeps
  asserting the field so the difference stays visible.
- **Actor-owned items are not crows on the server.** The client nominates the
  view entity's children as crows (`xr_object.cpp:405`, `Parent ==
  CurrentViewEntity()`); the server has no view entity, so the actor's
  inventory updates only on scheduled updates (crows 42.9 against 126.1 per
  frame). Item logic that runs in `UpdateCL` (weapon state machines among
  them) is actor-context work for Stage 3.
- **Seven objects 674.3–674.9 m from the actor came online on the client and
  not on the server** (online distance 675 m). Whether the server's ALife
  actor position (`CSE_ALifeCreatureActor::o_Position`, read by the switch
  manager) follows the live actor as it does on the client is not verified;
  check in S02-T06 before Stage 3 moves actors.
- The scheduler dispatch rate differs (5,690 against 1,640 per second); both
  sides run the same per-frame cycle budget (`psShedulerCurrent`,
  `xrSheduler.cpp:448`). The cause was not isolated; the stalker's own update
  rate matched.
- **Switch distance is 750 m** with factor 0.1, not the 150 m of vanilla
  content; the activity policy, not ALife switching, is what bounds per-frame
  work on this level (42.9 crows of ~305 active objects).
- Hand/toe hit boxes far from the body (S02-T03d) are unchanged by this task;
  they remain callback-driven bone poses at the sampled frame (G03).

## Limits

- **The comparison is not byte-for-byte.** Unlike the collision and physics
  captures, the two sides run different frame rates, the client's stalker
  moves under its Lua schemes before the walk, and the client's crow set
  includes presentation-driven objects; the compare tool asserts parameters,
  the stalker's identity and position, each side's pass rules and the game
  clock, and reports the rest. One asserted field differs (`objects_per_update`,
  see Findings).
- **One stalker, one short walk, one level.** The walked stalker was under
  script control, so its own planner did not run during the walk (the planner
  evidence is from the observation phase). No monster was walked, no combat,
  no ALife offline switch occurred (none is possible on this level under the
  content's distances).
- **The policy's cost was not measured against the client**: the crow and
  update counts are reported, not compared.
- **Anchors lag one frame for an actor spawned after the refresh**, by design
  (refresh after `ProcessGameEvents`); the first tick after the spawn uses the
  native spawn-time crow nomination.
- The server's ticks are real-time paced by the smoke driver.
