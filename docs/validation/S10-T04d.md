## What was built

**Per player by the engine (T04d-1).** The relation registry keeps community
goodwill per character id (`relation_registry.cpp:189-221`), the engine's
own hit and kill goodwill uses the attacker's id
(`relation_registry_actions.cpp:208`), and the server's participant
contexts already remap the installed scripts' `AC_ID` to the context's
player (S10-T04b, `CampaignScriptContext.cpp`). What remained were literal
character ids of 0 in the installed scripts (`set_community_goodwill_for_
faction`, the PDA's relations tab) and on a client the PDA reading character
0 (player 1): the three Lua exports `relation_registry.community_goodwill`,
`set_community_goodwill` and `change_community_goodwill` now map a character
0 to the context's player on the server (`campaign::info_actor_id`) and to
the client's own actor on a client (`campaign::local_view_actor`).

**A client's registry is fed (T04d-2).** `RELATION_REGISTRY::
SetCommunityGoodwill`, `SetCommunityRelation` and `CInventoryOwner::
SetReputation` (actors) call `campaign::coop_server_relation_changed`; the
server marks the affected player's link (goodwill, reputation) or queues the
faction pair (world) and `send_relations` (every tick after the survival
values) sends **CampaignEvent 18**: kind 1 the actor's goodwill with every
community (on change and on entering the world), kind 2 faction relations
(the whole table on entering in parts of 150 pairs, the changed pairs to
every client afterwards), kind 3 the actor's reputation (on change and on
entering). The client applies them to its own registry (`on_relations`),
which the PDA's relations tab (`relation_registry.community_goodwill(comm,
AC_ID)`, now its own actor) and the HUD's attitude colours read; the
reputation goes through `SetReputation` (the HUD's rank refresh).

**The faction table survives a restart (T04d-4).** relations-1 showed the
engine does not save the faction-vs-faction table: the installed
`game_relations.script` re-applies only its own changes, from `db.actor`'s
portable store (`drx_df_*`), which inside a participant context is one
player's store. The server now writes every pair the registry is told about
into the storage manager's state (`m_data.coop_relations`, saved with the
checkpoint) and applies the table once after a start (`relations-restore`),
before any client joins.

**Fixture (`--relations c1,c2`, profile `relations_party`, server-driven;
`relations_fixtures`).** In player 2's context the installed Lua export
changes the stalker goodwill of character 0 by −1000 (player 2's falls,
player 1's stays: the mapping), the stalker/bandit relation is set to 2000
(world), player 1's reputation is raised by 100, and a checkpoint is
published so the external kill and restart recover the registry.
`compare-coop-relations.py` checks the eight points in its header.

## Limits found here

- Relation changes are durable through the checkpoint only (T04d-3); the
  faction table is the server's own checkpoint state (T04d-4).
- The NPCs' behaviour toward each player (attitude per character) is the
  engine's and runs on the server; no fixture made an NPC hostile to one
  player and friendly to the other (the user's hands-on, or S10-T02a).
