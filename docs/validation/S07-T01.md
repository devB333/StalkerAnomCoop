# S07-T01 — Specify recoverable state and critical transaction boundaries

**Status: Completed (2026-10-22).** Specification task; no engine or protocol
change, no build, no runtime test. Engine `c57fe5b9` + patches 0001–0041;
protocol `proto-build-32` (v1.5).

## Deliverable

[Persistence contract](../persistence-contract.md): the inventory of what the
native checkpoint holds and lacks for two actors (§1), the identities and
their ordering (revision, generation, epoch, operation, sequence; §2), the
state classes with their representation, durability point and recovery

## Question

What, exactly, must survive a crash of the dedicated server, in which form,
and at which point may a player be told that something is permanent; and
what is allowed to roll back? (plan.md S07-T01; D7; R07, R08.)

Every acknowledged critical effect in the contract has a representation the
adapter can re-apply (`ledger`, `death`, `respawn`, `entity`); transaction
bundles are the record plus the lifecycle messages that share its revision;
failure windows are explicit (§4, §5, §11). The plan's acceptance for S07-T01
is met on paper; the behaviours are not yet observed, which is S07-T02…T06's
work.

## Findings that shape the implementation

1. **The native save is not atomic and has no autosave.** `FS.w_open` writes
   the final `.scop` directly (`LocatorAPI.cpp:1409-1420`); the `.scoc` is a
   second file from Lua; `CAutosaveManager::shedule_Update` returns at once
   (`autosave_manager.cpp:51-55`). The plan's "autosave" for the respawn point
   (S07-T07) therefore means the server's own periodic generation.
2. **Identities do not survive a load.** The registry allocates new
   `EntityId`s for every object of a loaded checkpoint and adopts actors by
   spawn order (`CampaignIdentity.cpp:538-561`). The supplemental record (§5.1)
   and the restore step before the client stages (§7 step 6) are required for
   a journal record to name anything across a restart.
3. **The epoch is a constant.** `ServerConfig.authority_epoch = 1` and
   `ResyncBegin.authority_epoch = 1` (`CoopServerHost.cpp:2498, 702`); the
   guard would accept a restarted server's messages as the same epoch. It must
   be allocated durably at every start (§2, §7 step 4).
4. **A client stays in a stale world when the server goes.** `Ended` only
   logs (`CoopClientLink.cpp:2931-2948`); the fence in §8 is not optional.
5. **Operation ids restart with the client process** (`CoopClientLink.cpp:1836`),
   so a restarted client could collide with its own earlier accepted ids; the
   index is per `(player, id)` and the client seeds its counter from the
   clock (§2, S07-T05).
6. **A server restart from a two-actor checkpoint, and a load with a dead
   participant actor, have never run**; they are S07-T02's round-trip and
   S07-T07's restart scenario.

## Carried limits touched

- **L15** (checkpoint has no crash or journal guarantee; ownership, captured
  contexts, participant references and actor 2's script state are not

- **L28** (deaths in memory only): the `death` record and §9 are the plan for
  S07-T07.

## Limits of this task

- Paper only. Nothing here is observed behaviour; the Windows flush and rename
  semantics are cited from their documented contracts and are tested against
  process termination in S07-T02/T06, never against power loss.
- The synthetic fixture (§10) and every adapter are defined, not built.
- Stage 8 effects (items, quests, rewards) have their classes and phases but
  no payloads; those are defined by their tasks under this contract.
