# Retained networking and campaign interfaces: focused source evidence

Investigated 2026-10-15. Repository `engine/xray-monolith`, commit `c57fe5b9fab4fe0506659db03137c52d2500eb2f`. All paths below are relative to that repository's `src/`. These are confirmed **source-level facts only**; no build, connection test, installed-binary correspondence, or runtime behavior is claimed. Source was read without modification. Scope is retained transport, authority boundaries, identity, and representative campaign mutation/persistence interfaces.

## Existing multiplayer is substantial, but single-player uses local messaging

- `xrNetServer/NET_Server.cpp:245–251`: `IPureServer::Connect` sets `psNET_direct_connect` when options contain `/single`. Its other path creates a DirectPlay server COM object (317–333), hosts it through `NET->Host` (390–432), and sends through `NET->SendTo` (614–658). `xrNetServer/NET_Client.cpp:377–385,988–1025` similarly contains remote connection and DirectPlay send code. These implementations are not empty stubs. Whether they work in a current Windows installation is untested.
- `xrNetServer/NET_Messages.h:6–13`: `net_flags` maps reliability to `DPNSEND_GUARANTEED`, optional unordered delivery to `DPNSEND_NONSEQUENTIAL`, and priority/immediate flags. This is a reuse point for transport adaptation, not evidence of per-stream ordering, application deduplication, snapshot baseline management, or encryption.
- `xrGame/Level_network.cpp:294–312`: `CLevel::Send` invokes `Server->OnMessage` directly with client ID 1 in direct-connect mode; a colocated server can use `OnMessageSync`; otherwise it uses `IPureClient::Send`.
- `xrGame/xrServer.cpp:797–812`: `xrServer::SendTo_LL` dispatches to `Level().OnMessage` for the server client or direct-connect mode and buffers actual network delivery otherwise. Thus networking-shaped SP APIs do not establish a remotely authoritative campaign.
- `xrServerEntities/object_factory_register.cpp:198–224` registers SP and legacy deathmatch/team/artifact client/server game classes, conditional on `NO_XR_GAME`, `NO_SINGLE`, and `BENCHMARK_BUILD`. `xrGame/xrGame.vcxproj:2923` includes `game_sv_mp.cpp`. `xrGame/xrServer_Connect.cpp:40–88` creates a game type from the connection options, initializes it, and delegates to transport. Legacy MP is retained, not proven enabled in the installed build.

## Existing authority is insufficient for this project

- `xrGame/xrServer_process_update.cpp:7–58`, `xrServer::Process_update`: requires `CL->flags.bLocal`, consumes u16 entity IDs and u8 record lengths, and invokes `CSE_Abstract::UPDATE_Read` on client-supplied state. `Process_save` (60–95) likewise requires the local client and imports per-entity `load(P)` records. The local simulation client is a special trusted participant; a dedicated backend must own that simulation independently of either player client.
- `xrGame/xrServer_process_event.cpp:13–71`: parses timestamp/type/destination, invokes entity `OnEvent`, broadcasts several outcome/state messages directly, and forwards `GE_INV_ACTION` to `SV_Client`. `GE_HIT` becomes a delayed game hit event (145–155). `xrGame/game_sv_base.cpp:735–749,778–795` resolves source/destination, runs `OnHit`, then broadcasts the packet. This inspected path does not recompute projectile/ray collision, fire cadence, ammunition, or damage from player input. A reliable packet is not validation.
- `xrGame/xrServer_process_event_ownership.cpp:14–95`: checks parent/item existence and local server-client object validity; rejects an already-parented item; permits the server client or new owner's client; rejects dead MP owners; calls `game->OnTouch`; migrates ownership; updates `ID_Parent` and children; broadcasts. These are meaningful reusable consistency checks. They are not a durable, idempotent transaction: this handler has no operation ID, state revision, commit log, atomic reward/currency bundle, or range/line-of-sight validation.
- `xrGame/game_sv_single.cpp:26–32,92–113`: SP explicitly creates `CALifeSimulator` with `/alife`; `OnTouch` attaches inventory items to the ALife graph. Moving authority must preserve this graph relationship, not just synchronize UI inventory lists.
- `xrGame/Actor_Network.cpp:88–158,290–314,387–401,419–500` retains actor export/import and remote physics paths; `net_Import_Base` applies health on clients, and local client actor paths skip portions of import. These are useful serialization/presentation starting points, not proof of server-reconciled input simulation.

## Entity and save serialization constraints

- `xrServerEntities/xrServer_Object_Base.h:71–77`: version and entity/parent/phantom identifiers are u16; `0xffff` denotes missing parent/phantom. `xrGame/xrServer.h:145–155` configures IDs 0 through 65534; `xrGame/xrServer.cpp:873` frees entity IDs. These IDs must not become globally stable campaign identities without an epoch/generation mapping.
- `xrServerEntities/xrServer_Object_Base.cpp:198–235,275–345`: `Spawn_Write`/`Spawn_Read` serialize entity IDs, flags, versions, and spawn state with legacy version branches. Reuse through a versioned adapter after compatibility tests; do not expose these internal packets as a durable public protocol.
- `xrGame/alife_storage_manager.cpp:72–119`: `CALifeStorageManager::save` invokes optional Lua callbacks, serializes header, world time, spawns, objects, and registry to memory, compresses it, then opens the final `$game_saves$` name and writes version/size/data. This is an existing world snapshot interface. The inspected routine does not implement a transaction log or atomic checkpoint publication, and callback-managed extra files require explicit consistency handling.
- `alife_storage_manager.cpp:126–154`: load calls the Lua hook, reconstructs header/time/spawns/objects, and reserves saved IDs through `PerformIDgen`, verifying equality. Native save compatibility and complete coverage of online client state remain to be tested.
- `xrGame/game_sv_single.cpp:241–256`: save/load delegates into ALife. `xrGame/InventoryOwner.cpp:177–201` saves/loads character information, name, and money; item structure is not solely this record. Relevant callbacks include item take/drop and belt/ruck/slot (338,502,517,528,541), which can trigger additional script effects.

## Quests and dialogue require native as well as Lua authority changes

- `xrGame/GametaskManager.cpp:22,47–68`: global active task ID; task registry initialized with fixed key 0 (commented as actor ID). `GiveGameTaskToActor` (94–131) checks an in-progress task ID, adds a task, reads `Level().GetGameTime`, invokes arrival/state callbacks, selects it, and updates PDA presentation. `UpdateTasks` (161–205) mixes task state evaluation with map pointers and pause state.
- `xrGame/GameTask.cpp:40–60`: `CGameTask::SetTaskState` sets state then performs completion/failure info transfers and Lua functions. It does not itself guard against reapplying the same terminal state. `ChangeStateCallback` (137–139), `CheckInfo` (172–181), and `SendInfo` (205–209) directly use `Actor()`. Task progression is not exclusively Lua: native condition evaluation (142–169) checks time, info flags and Lua predicates.
- `xrGame/PhraseDialog.cpp:85–129`: `CPhraseDialog::SayPhrase` identifies speaker objects, invokes the chosen phrase's script action, then determines allowed next phrases. `xrGame/PhraseScript.cpp:156–166,234–270`: `CDialogScriptHelper::Action` transfers information and invokes Lua callbacks with speaker objects. This can be a server action boundary, but script effects are presently embedded in dialog execution. Repeat/collision/dead-NPC checks must precede committing consequences.

## Proposed reuse boundary (design, not observed implementation)

Keep engine entity factories, native simulation behavior, ALife graph operations, spawn/state serializers behind adapters, and useful remote actor presentation code. Replace/adapt DirectPlay transport behind a narrow interface; avoid preserving trusted-player outcome semantics. Move the existing trusted simulation role into a dedicated authoritative process. Introduce stable campaign entity identity mapped to native IDs; server-validated intentions; one authoritative mutation order; operation IDs and expected revisions; atomic inventory/quest/world consequences; and committed change replication.

Persistence should start by validating complete native checkpoints, then add a durable commit journal and canonical identity mapping. Arbitrary engine callbacks/physics are not proven deterministic, so replaying raw inputs after a crash is not yet safe. Journal replay should use versioned committed state effects and explicitly tested recovery boundaries; do not claim exactly-once semantics based solely on reliable transport.
