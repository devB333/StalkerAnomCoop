# S02-T06 — Native campaign simulation and checkpoint round-trip

Recorded 2026-10-18 UTC. **Completed (2026-10-18).** This report covers the first
S02-T06 item, the actor's Lua binder on the server, which S02-T04c found not
running its first update. Part 1 isolates the cause (a native fault in a HUD
accessor swallowed by the binder, then a fatal Lua error from a HUD script);
the user decided on an inert server-side game UI (blocker B20, option 1);
part 2 (S02-T06a) implements it: the actor's binder now completes its first
update on the server, `objects_per_update` drops to the client's 20, both
fixtures pass and the server stays real-time. Part 3 (S02-T06b) shows the
ALife actor following the live actor. Part 4 (S02-T06c) shows a whole fight
between a stalker and a spawned monster running headless, on the server and
on the client. Part 5 (S02-T06d) shows the native checkpoint round-trip: the
server saves through the host's own path, restarts the level from the
checkpoint and gets its state back, and the normal client loads the same
checkpoint and matches. Part 6 (S02-T06e) shows a quest given, carried across
the checkpoint, completed and carried across a second checkpoint, on the
server and on the client. The G02 evidence record is [G02.md](G02.md).

## Part 1 — why the actor's first update never ran (patch 0015)

### Question

`compare-06-smoke-57` (S02-T04c) showed `objects_per_update` 65534 on the
server against 20 on the client. `bind_stalker.script` `actor_binder:reinit()`
sets 65534 at spawn and the first-update block of `actor_binder:update()`
(lines 207–240) queues the reset to 20, prints `collectgarbage before=` and
sets `db.actor.afterFirstUpdate`. The server log had none of that.

### Diagnostics added

- **`xrGame/script_binder.cpp`**: the binder's `try { … } catch (...) {
  clear(); }` blocks deleted the Lua binder silently. xrGame builds with C++
  exceptions off (`ExceptionHandling=false`) and luabind with
  `LUABIND_NO_EXCEPTIONS`, so Lua errors go to `CScriptEngine::lua_error` /
  `lua_pcall_failed` (which is fatal, `script_engine.cpp:266-288`) and never
  reach those catches; what they do catch are structured exceptions (access
  violations) in native code called from Lua. `shedule_Update` now uses an SEH
  filter that logs the exception code, the faulting address and the call
  stack with symbols (dbghelp `SymFromAddr`/`SymGetLineFromAddr64`,
  `CaptureStackBackTrace`) before clearing the binder; the other catches log
  the object and phase.

### Blocker B20 and the decision

Evidence from the installed scripts (`db/configs/scripts.db0`, read with
`tools/xray-db-extract.py`): 28 scripts subscribe to `actor_on_first_update`
(gameplay such as `alife_storage_manager`, `game_setup`, `itms_manager`,
`tasks_*`, `axr_companions`, and HUD such as `actor_status`, `actor_effects`,
`ui_*`), 27 to `actor_on_update`; `get_hud()` is used at 61 sites in 30
scripts, `ActorMenu.get_*` at 17 sites in 7 scripts, some unguarded. A Lua
runtime error in a binder call is fatal on both products. So without a game
UI the server could not run the actor's binder as installed. Options were
recorded (inert server game UI; a server script profile; non-fatal Lua errors;
deferring the binder to Stage 3). **The user chose the inert server game UI
(2026-10-18):** `CurrentGameUI()` returns a CPU-only, never-drawn game UI so
the HUD calls are harmless; it is a presentation shim, not a player (D4
unchanged).

## Part 2 — S02-T06a, the inert server game UI (patch 0016)

Patch `0016-inert-server-game-ui.patch` (SHA-256
`fe0909a17873340418a6011f6242391f138deaa7ae89d62219c683caf83bfa01`, 8 files);
the series reconstructs every changed file byte for byte in
`builds/stage2/patch-check-17b` (`builds/logs/patch-reconstruction-17.json`).

### Design

The client's own construction path builds the UI; the server runs it with the
same CPU-only resource rules as its models and materials
(`CpuOnlyResources`: shader, texture, geometry and buffer creation skipped
and counted), and never updates or draws it:

- **UI core and fonts** (`GamePersistent.cpp`, campaign branch of
  `OnAppStart`): `m_pUI_core = xr_new<ui_core>()` creates the cursor and the
  font manager (fonts read their `.ini` metrics; their shaders are skipped).
  The UI lays out against `Device.dwWidth/dwHeight`, which no window set on
  the server, so they are set to the UI base resolution (1024×768, with
  `fWidth_2`, `fHeight_2`, `fASPECT`) when zero. Deleted in `OnAppEnd`.
- **HUD manager** (`xrEngine/IGame_Level.cpp`): `g_hud` is created on the
  server too (its hit-marker and crosshair shaders are skipped); the
  render-level load stays skipped.
- **Game UI** (`Level_network_start_client.cpp`, unchanged code): with
  `g_hud` present, `g_hud->Load()` runs `game_cl_Single::createGameUI()` —
  the real `CUIGameSP` with `CUIActorMenu`, `CUIPdaWnd`, `CUIMainIngameWnd`,
  `CUIMessagesWindow`, talk and level-change windows — exactly as on the
  client.
- **Inert:** `CHUDManager::OnConnected` does not add the game UI to the frame
  sequence on the server, and `CHUDManager::OnFrame` returns at once there
  (no UI update, no camera pick, no player-hud animation). Nothing renders
  because the server has no render frame.
- **Checks:** the loaded report expects `hud=1 game_ui=1 ui_in_frame=0` and
  reports `actor_menu pda_menu maingame messages`; the tick report prints
  `S02-T06 timing` (script binder updates, total and the actor's) and
  `S02-T06 frame_ms` (`SLevelFrameTiming` in `CampaignActivityPolicy.h`,
  accumulated in `CLevel::OnFrame`: game events, object update, level script
  process, physics and script commanders, Lua GC step).

### Findings

- **The in-game HUD window's update is expensive without a device**: ~100 ms
  per frame on the server (`CUIMainIngameWnd::Update` and its children via
  `CHUDManager::OnFrame`), against a few ms on the client. Not investigated
  further since the inert UI is never updated; if a Stage 3 design wants
  server-side UI updates, profile it first.
- **Nominal device resolution.** `Device.dwWidth/dwHeight` were 0 on the
  server; the UI (and anything else reading them) now sees 1024×768. Record
  any other reader that cares (camera aspect is unused without a view entity).
- **The game UI constructs CPU-only without a single device fault**: 1,797
  shaders and 1,572 textures were already skipped before it; the UI's own
  skips are included in the same counters. Lua-created UI windows
  (`UIIndicators()` in `actor_status`) construct too.
- The actor's binder costs ~5.5 ms per scheduled update on the server (27
  `actor_on_update` subscribers), every tick (`t_min = t_max = 1`): about a
  quarter of a 20 ms tick. R11 material for Stage 3 (two actors).
- Offline ALife scheduling dropped from ~91 to ~1.4 object advances per tick
  once `objects_per_update` reached 20: the S02-T04c R11 note was an artefact
  of the broken binder.

### Limits

- The inert UI is construction-only: dialogs shown by scripts
  (`ShowDialog`), custom statics with lifetimes and messages accumulate in
  objects that are never updated; `AddCustomStatic` keeps working but its
  statics never expire on the server. Any script reading UI *state* (not
  constructing it) gets client-default values.
- Fonts and the cursor exist for layout only; nothing measures text on the
  server beyond what construction does.
- Save/reload, combat and the ALife actor position (S02-T06 items) are not
  yet attempted; the actor's binder save (`alife_storage_manager`) is now
  reachable for the save round-trip.
- The client comparison is behavioural, not byte-for-byte (different frame
  rates and durations); the asserted rules and the stalker's footstep files
  match.

### Fixture (`xrGame/CampaignCombatCapture.{h,cpp}`)

  (`CALifeSimulatorBase::spawn_item`, `alife_simulator_base.cpp:98-146`, the

  `alife_switch_manager.cpp:160-250`, reached through the level registry's

### Findings

- **Quests work headless end to end.** Giving through the installed dialogue
  functions, both halves tracking the task, the fetch status functor,
  the turn-in, completion through the native task manager's frame update and
  its Lua callback, and every `on_complete` effect (money, goodwill, info
  portion, item removal, DRX bookkeeping) ran on the campaign server with no
  device, UI window or client, and the same on the normal client.
- **Quest state persists on both halves.** The native task crossed both
  checkpoints in the ALife registry (same receive time, state), the Lua task
  entry crossed the first through the marshal (`loaded=1`) and its retirement
  the second, the fetch item through the portable store, and the rewards
  through the actor's money, the relation registry and the info portions.
  The client loaded the server's completed checkpoint to the server's exact
  money, goodwill and info state.
- **The reward differs per run by design**: `fetch_reward_and_remove` pays
  the item's value within ±10 % at random (server 9,700, client 11,050 for a
  7,000 kit at ×1.25 … the configured multiplier is absent for this task, so
  the base is the value plus the DRX bonus); the rules assert an increase.
- **B21: monster AI bound to the controlled entity.** `CPsyDogAura` takes
  the actor from `Level().CurrentEntity()` and dereferences it; `CPhantom`
  (psi-storm phantoms) and `CAI_Trader::LookAtActor` do the same unguarded;
  `CBaseMonster::SetAttackEffector` and the pseudogiant's earthquake check
  for null. The server controls no entity (D1), so the first psy dog online
  near the base crashed its `Think`. The aura is a camera post-process, so
  patch 0020 skips it with no controlled entity; the phantom and the trader
  are unchanged and recorded for Stage 3, where "which actor" becomes a
  participant question ([boundary B21](../headless-service-boundary.md)).
- **Level registry after a load vs. at the save.** A squad member that was
  online (directly controlled, individually registered) at the save is held
  under its group after the load; the ALife total is exact, the level
  registry one lower. Installed engine behaviour on the same load path the
  client runs; the checkpoint rule names each such object and accepts it.
- **Two fixture lessons** worth keeping: a child of an online parent must be
  spawned through the server (`alife():create`'s binding), not registered
  offline, or the level stop asserts; luabind proxies and default-constructed
  objects are not safe to inspect from C++ after a level restart, so Lua
  state is read through a plain-table helper.

### Limits

- One quest, one giver, one level, one fetch item placed by the fixture (the
  player did not find it in the world). No storyline task, no timed task, no
  failure path, no cancellation, no task from a simulation NPC, no
  multi-stage task.
- The dialogue window is not shown on either product; the fixture calls the
  phrase functions the window would call. Phrase availability conditions
  other than the task list (reputation, money, info portions gating the
  dialog tree) were not evaluated.
- The quest fixture moves the actor to the giver and spawns the item; both
  are fixture stimuli, like the combat fixture's monster.
- Only the task manager's own state is compared; the PDA presentation, the
  news messages and the map spots are not observed.
- The G02 gap "task execution" is closed to this extent; wider coverage is
  Stage 3 and later work.
