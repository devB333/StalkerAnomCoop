# S10-T05b — Every quest is a party quest (general task types under the party policy)

**Status: Completed (2026-10-29).** Engine `c57fe5b9` + patches 0001–0059
and 0060 (`party-tasks-general`, replacing the work-in-progress export of
the same name); protocol unchanged (`proto-build-49`, v1.6). Builds:
**campaign-316 / client-213**. Gameplay decisions for G10: [Stage 10
decisions](../stage10-decisions.md) T05b-1…T05b-5 (T05b-1 and T05b-2 taken
with the user before the task started). Narrows **L10**.

## What was built

**Every task the task ini knows is the party's (T05b-1).** The per-task
allow list of S08-T04 (`kPartyTasks`, one fetch task) is gone:
`party_task_supported(id)` asks the installed task ini
(`task_manager.task_ini:section_exist`), so any of the 611 `tm_*.ltx`
sections is accepted and turned in through the S08 party path, whichever
player asks (the talk window's accept and finish phrases, S10-T04a, or the
intent). The talk hooks were factored into `party_accept_task` and
`party_turn_in_task`, which the fixture calls directly. After a restart
`rebuild_party_tasks` registers **every in-process native task** as the
party's (held by the anchor, participant 1's actor, with its saved
instance), not just the listed one. The accept news names the task by its
translated title.

**Progress is the installed scripts' own, made party-wide by the server
(T05b-3, T05b-5).**

- *A task scope sees the party's inventory.* While a task's own check or
  completion runs on the server (`ScriptContextScope(const CGameTask*)`,
  `GameTaskManager.cpp:203`, `GameTask.cpp:169`),
  `CScriptGameObject::GetObjectByName` and `IterateInventory` on a
  participant actor also search the other participant actors' inventories
  (`campaign::party_inventory_view`), so the 206 fetch-style status functors
  (`actor_has_fetch_item`, the lostzone steps, DoctorX item tasks) count
  the party's items without a Lua wrapper each. The Stage 8 fetch wrapper
  (progress pooled, money per own items) stays on top.
- *A kill or a hit by a participant actor is "the player's".*
  `CEntityAlive::Die` and `CHitMemoryManager::add` run the installed death
  and hit callbacks inside the attacker's participant context when the
  attacker is a participant actor, so `AC_ID` and `db.actor` name the
  killer (the bounty tag `tagged_by_actor`, `npc_on_death_callback`,
  statistics). Off the campaign server the scope refuses and nothing
  changes.

**The reward goes to both players in full, the same amount each (T05b-2).**
While a party turn-in is pending (`P.turnin`) the Lua adapter wraps the
general reward paths that the installed `on_complete` condlists and
`CGeneralTask:give_reward` use, resolving instead of applying:
`dialogs.relocate_money` type `in` (one payment per participant actor, the
same sum), `dialogs.relocate_item_section` type `in` and
`xr_effects.reward_item` (one give per participant actor), and
`task_objects.CGeneralTask.give_reward` itself, which
`task_manager.task_callback` always calls on completion and so marks the
effects resolved (`done`) for any task type. `apply_party_effects` then
pays each actor natively (`set_money`), spawns the item rewards on each
actor (`give_to`) and applies the goodwill changes to each, with news per
actor and `quest-paid` / `quest-item-given` / `quest-goodwill` lines.
`complete_task_inc_goodwill` was already resolved per actor by S08.

## Limits found here

- **One general task type was run** (a bounty, `bounty_task`): the fetch
  family has S08's evidence, the other status-functor families (assault 80,
  lostzone 34, DoctorX 41, hostage, spy, measure, delivery, fate, …) share
  the same accept, rebuild, turn-in and reward path but had **no run**; a
  per-family check is the matrix's F-rows for S10-T05c (storyline chains)
  and later children. Decision rows T05b-3…T05b-5 are the policies they run
  under.
- **Item rewards through `xr_effects.give_reward`** (stored rewards:
  `alife_create_item` directly) and any `alife_create_item(section,
  db.actor)` outside `reward_item` go to the anchor only; `reward_item`
  (incl. `reward_random_item`) and `relocate_item_section` reach both. A
  multi-use item given through `reward_item` gets the section's default
  uses on both (the installed `uses` roll is not replayed).
- **Money costs inside a task are the anchor's purse** (T05b-4, a limit):
  `db.actor:money()` checks and `transfer_money` fees in a task's own
  logic read and charge participant 1's actor.
- **A fail or cancel** (`on_fail`, `on_cancel`) is not resolved per actor:
  `fail_task_dec_goodwill` is not wrapped, so a failed task's goodwill
  penalty is applied natively in the task owner's (anchor's) context, once,
  as in single player. No run.
- The fixture kills the target online after an ALife teleport; the
  engine's offline `kill_entity` is unusable on a stalker with items (the
  installed scripts never call it either: offline deaths release the
  object through `squad:remove_npc`). A bounty whose target dies offline in
  the installed offline combat is released, and the installed
  `bounty_task` functor then reads it as **failed** — single-player
  behaviour, unchanged here.
- The installed `npc_on_death_callback` credits the bounty when
  `who:id() == 0` (actor 0 literally) or the target was tagged by a hit
  with `AC_ID`; player 2's kill without a prior hit takes the installed
  "complete anyway" branch (stage 1 either way). With a hit first, the hit
  callback in player 2's context tags it (`AC_ID` = player 2).
